# 12　C++ 侧落地：三条路径

对 C++ 工程师来说，这一章是全书最"能用"的部分。三条主路径：**llama.cpp（LLM 专用）、ONNX Runtime（通用图）、TensorRT（NVIDIA 极致）**。

## 12.1 llama.cpp：从 GGUF 到推理

### 编译

```powershell
git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp
cmake -B build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j 16
```

不开 CUDA 就是纯 CPU 版本，能跑但慢。**现代 x86 一定要开 `-DGGML_AVX2=ON`（默认会检测）**，这是 CPU 侧最大的性能变量。

### 加载与推理

```cpp
#include "llama.h"

llama_backend_init();
auto mp = llama_model_default_params();
mp.n_gpu_layers = 99;          // 全部层放 GPU；-1 表示不 offload
auto* model = llama_model_load_from_file("qwen2.5-7b-q4_k_m.gguf", mp);

auto cp = llama_context_default_params();
cp.n_ctx   = 4096;             // 上下文长度
cp.n_batch = 512;              // 单次提交的最大 token 数（prefill 分块）
auto* ctx = llama_init_from_model(model, cp);

// 取 tokenizer
const llama_vocab* vocab = llama_model_get_vocab(model);
auto toks = llama_tokenize_wrapper(vocab, "你好", true, true);
```

关键参数的含义：

| 参数 | 作用 | 调法 |
| --- | --- | --- |
| `n_gpu_layers` | 多少层放显存 | 显存放得下就全放；混合模式按显存估算 |
| `n_ctx` | 上下文长度 | 越大越吃内存（KV cache） |
| `n_batch` | prefill 分块大小 | 大则首 token 快，吃显存 |
| `n_threads` | CPU 线程数 | 设为物理核数，超线程无益 |
| `type_k/type_v` | KV cache 精度 | `GGML_TYPE_Q8_0` 省一半显存 |

### 采样链

llama.cpp 的采样是一个链式结构，顺序影响结果：

```cpp
auto* smpl = llama_sampler_chain_init(llama_sampler_chain_default_params());
llama_sampler_chain_add(smpl, llama_sampler_init_top_k(40));
llama_sampler_chain_add(smpl, llama_sampler_init_top_p(0.9, 1));
llama_sampler_chain_add(smpl, llama_sampler_init_temp(0.7));
llama_sampler_chain_add(smpl, llama_sampler_init_dist(seed));
```

**顺序建议**：先 top-k/top-p 截断，再温度，最后按分布采样。反过来做会先软化再截断，效果差别不小。

### 流式输出的正确姿势

```cpp
while (generated < max_tokens) {
    auto* cur = llama_get_logits_ith(ctx, -1);      // 最后一个 token 的 logits
    int id = llama_sampler_sample(smpl, ctx, -1);
    if (llama_vocab_is_eog(vocab, id)) break;       // EOG = end of generation
    callback(detokenize(id));                       // 立刻推给客户端
    llama_batch batch = llama_batch_get_one(&id, 1);
    llama_decode(ctx, batch);                       // 单 token 解码
}
```

**每步只喂 1 个 token** 是 decode 的标准做法，KV cache 会自动复用。

## 12.2 三个必须自己管的资源

| 资源 | 怎么管 | 不做的后果 |
| --- | --- | --- |
| model | 进程级单例，加载一次 | 每次请求加载 → 秒级延迟 |
| context | 每会话一个，或池化复用 | 上下文泄漏 → 请求间串味 |
| KV cache | 随 context 分配 | 并发时显存爆 |

**context 复用要小心**：多轮对话需要保留历史 KV；但新会话必须 `llama_kv_cache_clear`，否则上一个用户的内容会污染下一个。

## 12.3 ONNX Runtime：通用但有边界

```cpp
Ort::Env env(ORT_LOGGING_LEVEL_WARNING, "app");
Ort::SessionOptions so;
so.SetIntraOpNumThreads(8);
so.SetGraphOptimizationLevel(ORT_ENABLE_ALL);     // 图优化级别
// 可选：so.AppendExecutionProvider_CUDA(0);
Ort::Session sess(env, "model.onnx", so);

// 输入输出名只需取一次，缓存起来
auto in_name  = sess.GetInputNameAllocated(0, allocator);
auto out_name = sess.GetOutputNameAllocated(0, allocator);

// 复用缓冲，避免每帧分配
std::vector<float> in_buf(N);
Ort::MemoryInfo mem = Ort::MemoryInfo::CreateCpu(OrtArenaAllocator, OrtMemTypeDefault);
Ort::Value in_tensor = Ort::Value::CreateTensor<float>(mem, in_buf.data(), N, dims, 4);
auto out = sess.Run(Ort::RunOptions{nullptr}, names_in, &in_tensor, 1, names_out, 1);
```

四个高频问题：

- **每帧新建 Session**：初始化可能 1–3 秒，必须复用；
- **动态维度没声明**：导出时 `dynamic_axes` 漏了，换 batch 就报错；
- **算子不支持**：`ORT_ENABLE_ALL` 后仍有算子回退到 CPU，性能骤降。用 `sess.GetProfilingInfo` 查；
- **线程过度订阅**：`intra_op` 与 `inter_op` 都设大，反而抢核。intra 设物理核，inter 设 1–2。

## 12.4 TensorRT：性能上限，构建成本高

TensorRT 需要针对"具体 GPU + 具体形状"编译引擎：

```cpp
auto builder = nvinfer1::createInferBuilder(logger);
auto net = builder->createNetworkV2(1U << int(nvinfer1::NetworkDefinitionCreationFlag::kEXPLICIT_BATCH));
// 解析 ONNX -> network -> config（设精度、设 profile 的 min/opt/max 形状）
auto engine = builder->buildSerializedNetwork(*net, *cfg);
```

| 优点 | 代价 |
| --- | --- |
| 极致性能，算子融合彻底 | 构建耗时（分钟到小时） |
| 支持 FP16/INT8/FP8 | 换 GPU 架构要重编 |
| 有 kernel 自动调优 | 调试信息少，出错难定位 |

**什么时候值得用**：固定硬件、固定形状、追求极限吞吐。如果模型频繁变、硬件多样，ONNX Runtime 更省事。

## 12.5 一个最小服务骨架

```cpp
// 三件事：动态批、队列、超时
struct Req { std::string prompt; std::promise<std::string> done; };

void worker() {
    while (running) {
        std::vector<Req> batch;
        queue.wait_pop_batch(batch, /*max=*/8, /*wait_ms=*/5);  // 攒 5ms
        if (batch.empty()) continue;
        auto outs = engine.generate(batch_prompts(batch), /*max_new=*/256);
        for (size_t i = 0; i < batch.size(); ++i)
            batch[i].done.set_value(outs[i]);                    // 逐个兑现
    }
}
```

要点：**攒批窗口要短（2–10ms）**，长了延迟明显；**超时要独立于批处理**，不能因为一个慢请求拖累全批；**背压要早**，队列满了直接 429，别无限堆积。

## 12.6 性能定位顺序

1. 看 GPU 利用率：低 → 数据/调度瓶颈；高且吞吐低 → 带宽瓶颈；
2. 拆 TTFT 与 TPOT：TTFT 高是 prefill 问题（长 prompt、chunk 太小）；TPOT 高是 decode 问题（权重大、量化不够）；
3. 看显存：是否因 KV 溢出触发重算或换出；
4. 最后才是换引擎。
