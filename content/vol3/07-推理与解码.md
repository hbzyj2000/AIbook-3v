# 6　推理与解码：把生成做快

生成是一个 token 一个 token 吐出来的过程。这一章解释为什么它慢、以及六种加速手段各自在解决什么。

## 6.1 采样策略

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| 贪心 | 每步取最大概率 | 确定性任务（抽取、代码） |
| 束搜索 | 保留 k 条候选路径 | 翻译（但现代 LLM 少用） |
| 温度采样 | logits 除以 T 后 softmax | 通用，控制随机性 |
| top-k | 只在前 k 个里采样 | 抑制长尾垃圾 token |
| top-p（核采样） | 累积概率到 p 的最小集合 | 更自适应，常用 |
| min-p | 概率低于最大值的 p 倍就截断 | 高温下比 top-p 稳 |
| 重复惩罚 | 降低已出现 token 的 logits | 缓解循环复读 |

**经验配置**：抽取/代码用 `T=0`；创意写作用 `T=0.8–1.0 + top_p=0.9`；需要多样性但不想胡说，加 min-p。

@widget softmax

温度不只是"随机程度"，它改变的是分布的熵。T 很低时几乎等价贪心，T 很高时连低概率 token 都有机会——**这既带来创造力，也带来事实性下降**。

## 6.2 为什么 decode 慢：一次只出一个 token

生成第 $t$ 个 token 时，模型要做一次完整前向，但**只用到最后一行**的输出。也就是说，你付出了全部权重的读取成本（7B FP16 约 14GB），只产出了 1 个 token。

$$ \text{decode 的理论下限}=\frac{\text{权重字节}}{\text{显存带宽}} $$

A10 的带宽约 600 GB/s，14GB 权重 → 每 token 至少 23ms，即约 43 tok/s。**这就是单请求的物理上限**，再怎么优化算子也难以突破。想更快只有三条路：量化（减少字节）、批处理（一次读权重服务多个请求）、投机解码（一次前向出多个 token）。

## 6.3 KV cache：不存就重复算

自回归生成时，第 $t$ 步的注意力需要前面所有 token 的 K、V。如果每步都重算，总计算量是 $O(T^3)$；缓存下来后是 $O(T^2)$。

$$ \text{KV 大小}=2\times L\times S\times H_{kv}\times d_{head}\times B\times b $$

7B、32 层、8 个 KV 头、128 维、FP16、序列 4096：$2\times32\times4096\times8\times128\times2\approx537$MB/序列。**8 路并发就是 4.3GB**，还没算权重。这就是并发上不去的直接原因。

**前缀缓存（prefix caching）**：如果多个请求共享同一段前缀（系统提示、few-shot 示例、同一文档），这部分 KV 可以复用。多轮对话里尤其有效——每一轮都能复用之前的对话 KV。

## 6.4 批处理：连续批处理是关键

| 方式 | 做法 | 问题 |
| --- | --- | --- |
| 静态批 | 攒够一批一起跑，全部完成才返回 | 短请求等长请求，利用率低 |
| 连续批（continuous batching） | 每个 step 检查，完成的退出、新来的插入 | 实现复杂，需要分页管理 KV |
| PagedAttention | KV cache 按页分配，不要求连续 | 显存碎片大幅减少 |

**PagedAttention 的贡献更像操作系统**：把 KV cache 切成固定大小的块，用页表映射，于是不同序列的 KV 可以交错存放，显存利用率从 20%–40% 提到 90% 以上。vLLM 就是靠这个把吞吐提升数倍。

## 6.5 量化：三种主流格式

| 格式 | 精度 | 特点 | 适用 |
| --- | --- | --- | --- |
| GPTQ | 4bit 权重 | 训练后量化，需校准数据 | GPU 部署 |
| AWQ | 4bit 权重 | 保护重要通道，精度更好 | GPU 部署 |
| GGUF | 2–8bit 多种 | llama.cpp 生态，CPU/混合推理 | 本地/端侧 |
| FP8 | 8bit 浮点 | 训练与推理都支持 | H100 等新卡 |
| INT8（SmoothQuant） | 8bit | 激活也量化，需校准 | 高吞吐服务 |

**经验结论**：4bit 权重量化通常掉 1–3 个点，7B 以上模型比小模型更抗量化。**KV cache 量化**（FP16 → INT8）能再省一半显存，但长上下文下精度损失更明显，需要实测。

## 6.6 投机解码：用便宜模型猜，用大模型验

思路：用一个小的草稿模型连续猜 $k$ 个 token，再让大模型一次前向并行验证。被接受的 token 直接采用，第一个被拒绝的位置之后重新采样。

$$ \text{加速比}\approx\frac{1}{1-\alpha}\ \text{（}\alpha\ \text{为接受率）} $$

接受率取决于草稿模型与目标模型的一致性：同族的小模型效果最好（如 1B 猜 7B）。加速通常 1.5–3 倍，**不改变输出分布**（有严格的接受-拒绝校正）。

## 6.7 引擎选型

| 引擎 | 优势 | 局限 |
| --- | --- | --- |
| vLLM | 生态成熟、PagedAttention、吞吐高 | 自定义模型支持需适配 |
| SGLang | 前缀复用与结构化输出强 | 生态较新 |
| TensorRT-LLM | NVIDIA 上极致性能 | 编译耗时、平台绑定 |
| llama.cpp | CPU/端侧、GGUF 生态 | 高并发弱 |
| ONNX Runtime | 通用、跨平台 | LLM 优化不如专用引擎 |

## 6.8 四个必看的指标

| 指标 | 含义 | 谁在意 |
| --- | --- | --- |
| TTFT | 首 token 延迟（prefill 时间） | 交互体验 |
| TPOT | 每输出 token 时间 | 阅读速度是否跟得上 |
| 吞吐（tok/s） | 单位时间总产出 | 成本 |
| 显存占用 | 权重 + KV + 激活 | 并发上限 |

**优化顺序通常是：先提吞吐（批处理、量化），再压 TTFT（前缀缓存、chunked prefill），最后调 TPOT（投机解码）。** 三者互相牵制，比如批越大 TPOT 越长。

:::eng 工程视角
不要凭感觉判断"模型慢"。先测出 TTFT 和 TPOT，再看 GPU 利用率：利用率低说明在等数据或调度；利用率高但吞吐低说明是带宽瓶颈；两者都正常但延迟高，可能是排队。**这套定位方法比换引擎有效。**
:::
