:abs 成本 = 显存 ÷ 并发 × 时间。三个变量里，只有"单位时间产出"能被优化。

# 13　成本与容量规划

上线前必须能回答三个问题：**能撑多少并发、单次请求多少钱、扩到十倍要加什么**。这一章给可算的公式。

## 13.1 三笔成本

| 成本 | 构成 | 量级感受 |
| --- | --- | --- |
| 训练 | GPU 小时 + 数据工程 | 7B 全量训练数十万到百万美元级 |
| 推理 | GPU 小时 + 显存占用 | 通常占长期成本的 80% 以上 |
| 运维 | 人力 + 存储 + 监控 | 常被低估，尤其是数据标注 |

**推理成本是长期的、持续的、随用户增长线性上升的**。所以推理优化（量化、批处理、缓存）的回报远高于训练优化。

## 13.2 容量公式

$$ \text{并发上限}=\frac{\text{显存}-\text{权重}}{\text{单序列 KV}},\qquad \text{单序列 KV}=2LSH_{kv}d_{head}b $$

举例：24GB 卡跑 7B INT4（权重 3.5GB）+ 8 层系统占用，剩约 19GB；单序列 KV（4K 上下文）约 0.5GB → **约 36 路并发**。如果上下文升到 16K，直接掉到 9 路。

$$ \text{吞吐}=\frac{\text{并发}}{\text{每 token 时间}}\times\text{并发}\ \Rightarrow\ \text{tok/s}\approx\frac{B}{\text{TPOT}} $$

注意 TPOT 会随批增大而变长，所以吞吐不是线性增长，存在饱和点。

## 13.3 单位经济：一次问答多少钱

假设：

- A10 实例 1.0 美元/小时；
- 输入 1000 token、输出 300 token；
- 实测吞吐 30 req/s（批处理下）。

$$ \text{单次成本}=\frac{1.0}{3600\times30}\approx0.0000093\ \text{美元} $$

看起来可以忽略。但如果吞吐掉到 0.5 req/s（没有批处理、上下文很长），就变成 0.00056 美元/次，一天十万次是 56 美元——**同一个模型，差 60 倍**。

**结论：成本不由模型大小决定，由"每 GPU 每小时能服务多少请求"决定。**

## 13.4 六种降本手段与收益

| 手段 | 收益 | 风险 |
| --- | --- | --- |
| 量化（FP16→INT4） | 2–4× 吞吐 | 精度掉 1–3 点 |
| 批处理 | 3–10× | 延迟上升 |
| 前缀缓存 | 20%–50%（多轮场景） | 命中率依赖请求结构 |
| 小模型路由 | 60%–80%（简单任务走小模型） | 需要分类器 |
| 输出长度控制 | 30%–50% | 可能损信息量 |
| 缓存完整回答 | 视重复率 | 需要语义去重 |

**路由是最被低估的一招**：把"打招呼、查天气、格式转换"这类请求分流给小模型或规则，能让大模型的负载下降一大半。

## 13.5 云 vs 自建

| 维度 | 云 API | 自建 GPU |
| --- | --- | --- |
| 启动成本 | 几乎为零 | 采购 + 部署数周 |
| 单位成本 | 高（含毛利） | 低（利用率高时） |
| 弹性 | 好 | 差 |
| 数据合规 | 数据出境风险 | 完全可控 |
| 定制 | 受限 | 完全自由 |

**判断标准**：月调用量低于某个阈值时，API 几乎总是更划算——因为你自建的 GPU 会有大量空转。粗略分界：单卡满载运行超过 6–8 个月，才值得考虑自建。

## 13.6 一个容量规划表

| 假设 | 值 |
| --- | --- |
| 日活请求 | 10 万 |
| 平均输入/输出 token | 1200 / 250 |
| 峰值/均值比 | 3 |
| 单卡吞吐（INT4 + 批处理） | 25 req/s |
| 单卡成本 | 24 美元/天 |

均值 QPS = 100000/86400 ≈ 1.16；峰值 ≈ 3.5。单卡能撑 25，看起来一张卡够，但要留冗余与故障切换：**至少 2 张，建议 3 张**，成本约 72 美元/天。

:::warn 常见坑
- 只按平均 QPS 规划，遇到活动峰值直接雪崩；
- 忽略"长尾请求"：99% 的请求很快，1% 的超长请求会占据整条链路；
- 不计算重试成本：失败重试会让实际调用量翻倍；
- 忘记缓存策略的维护成本（失效、更新、去重）。
:::
