# 0　导读：一条请求的完整链路

这一卷的组织方式很具体：**跟着一次推理请求往下走**。从字符串变成 token，进模型，经过几十层注意力与前馈，出 logits，被采样成下一个 token，再循环；如果接了检索，还要在前面插入一次向量查询；如果接了工具，还要在外面套一层决策循环。

每经过一个环节，都会有一笔账要算——显存、带宽、延迟、成本。**这一卷的重点就是把这四笔账算清楚**，让你能判断瓶颈在哪，而不是盲调参数。

## 0.1 七个阶段

| 阶段 | 输入 → 输出 | 主要成本 | 可优化点 |
| --- | --- | --- | --- |
| ① 预处理 | 文本 → token ID | CPU，可忽略 | 缓存、批处理 |
| ② 嵌入 | ID → 向量 | 一次查表 | 无 |
| ③ 编码（prefill） | 全部 prompt → KV | 算力密集 | FlashAttention、并行 |
| ④ 解码（decode） | 逐 token 生成 | 带宽密集 | KV cache、批处理、量化 |
| ⑤ 采样 | logits → 下一个 token | 可忽略 | 温度/top-p |
| ⑥ 后处理 | token → 文本 | 可忽略 | 流式输出 |
| ⑦ 编排 | 检索、工具、重试 | 网络与串行 | 并行、缓存、路由 |

**关键认识：prefill 是算力密集，decode 是带宽密集。** 这两个阶段的瓶颈完全不同，所以优化手段也不同——批处理对 decode 收益极大，对 prefill 收益有限；量化对两者都有效，但影响不同。

## 0.2 三个必须先算的数

进入细节之前，先把三个量级建立起来：

1. **权重显存**：$N$ 参数、$b$ 字节/参数 → $N b$ 字节。7B FP16 = 14GB，INT4 ≈ 3.5GB；
2. **KV cache 显存**：$2 \times L \times S \times H \times B \times b$ 字节（K 和 V，每层 $S\times H$）；
3. **每 token 计算量**：前向约 $2N$ FLOPs，训练约 $6N$（含反向）。

@widget kvcache

上面这个账本可以直接玩：把并发从 8 提到 64，你会看到 KV cache 迅速超过权重，成为显存的主要占用——**这是所有推理优化的起点**。

:::note 一点提醒
这一卷的所有数字都是**量级估算**，用于判断瓶颈，不能直接当 benchmark。真实数字必须在你自己的硬件上压测得到。公式给的是"往哪个方向优化"，不是"能优化多少"。
