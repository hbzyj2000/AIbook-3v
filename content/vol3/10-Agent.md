# 9　Agent：带约束的控制循环

第 10 章（卷二）讲过智能体的概念与适用边界。这一章讲**怎么把它做出来并且不出事**。

## 9.1 最小的可用结构

```python
while step < MAX_STEPS:
    plan = llm(messages)                    # 1. 决定下一步
    if plan.is_final:                       # 2. 结束条件
        return plan.answer
    tool, args = plan.tool_call             # 3. 解析工具调用
    validate(tool, args)                    # 4. 参数校验（白名单 + schema）
    result = tools[tool](**args)            # 5. 执行（带超时）
    messages.append(observation(result))    # 6. 观察写回上下文
```

六个位置都可以加护栏，**每一处都对应一类真实故障**：

| 位置 | 故障 | 护栏 |
| --- | --- | --- |
| 规划 | 绕圈、目标漂移 | 最大步数、目标重述、无进展检测 |
| 解析 | 调用了不存在的工具 | 工具白名单、JSON schema 校验 |
| 执行 | 超时、异常、副作用 | 超时、重试上限、幂等设计 |
| 观察 | 结果太长撑爆上下文 | 截断、摘要、只保留关键字段 |
| 结束 | 永远不结束 | 步数上限 + 兜底回答 |
| 全局 | 越权操作 | 权限分级、危险动作人工确认 |

## 9.2 工具设计：schema 就是接口契约

工具的 JSON schema 写得好不好，直接决定调用成功率。四条原则：

1. **参数少而明确**：三个参数以内，避免 `options` 这种自由对象；
2. **枚举代替自由文本**：能枚举的值一定枚举，减少幻觉；
3. **描述写"什么时候用"**，不只是"是什么"。模型靠描述决定要不要调；
4. **返回结构化结果**，包含成功/失败与错误码，便于模型决策重试。

```json
{
  "name": "search_docs",
  "description": "在内部知识库检索。当问题涉及公司制度、流程、产品参数时使用；闲聊不要调用。",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string", "description": "检索关键词，中文，不超过 30 字"},
      "top_k": {"type": "integer", "enum": [3, 5, 10], "default": 5}
    },
    "required": ["query"]
  }
}
```

## 9.3 规划：三种粒度

| 粒度 | 做法 | 适用 |
| --- | --- | --- |
| 无规划 | 边想边做（ReAct） | 步骤少、路径不确定 |
| 一次性计划 | 先列步骤再执行 | 步骤明确、可并行 |
| 滚动规划 | 每步重估剩余计划 | 长任务、环境会变 |

**经验**：任务步数少于 5 步，ReAct 足够；超过 10 步，一定要有显式计划与进度记录，否则模型会迷路。

## 9.4 记忆：三层

| 层 | 存什么 | 实现 |
| --- | --- | --- |
| 工作记忆 | 当前任务的消息与中间结果 | 上下文窗口（会被截断） |
| 会话记忆 | 跨轮次的关键事实 | 摘要 + 结构化槽位 |
| 长期记忆 | 用户偏好、历史结论 | 外部存储 + 检索 |

**最容易被忽略的是"摘要压缩"**：长任务里上下文必然超限，需要定期把已完成步骤压成一段摘要。压缩策略要保留"结论与未完成项"，丢弃"过程细节"。

## 9.5 多智能体：什么时候值得拆

拆分的收益来自**上下文隔离**：不同角色只需要看自己相关的信息，上下文更短、更聚焦。拆分的代价是通信开销与一致性维护。

值得拆的信号：

- 子任务需要完全不同的工具集；
- 子任务可并行；
- 需要独立评审（一个生成、一个挑错）。

不值得拆的信号：

- 任务步骤少；
- 强依赖共享上下文（拆开反而要反复传递）；
- 团队没有能力维护多套提示与评测。

## 9.6 评测：智能体不能只看最终答案

| 维度 | 指标 | 采集方式 |
| --- | --- | --- |
| 任务成功率 | 端到端通过率 | 固定任务集，人工或规则判定 |
| 步数效率 | 平均步数 / 最优步数 | 日志统计 |
| 工具正确率 | 参数合法、调用必要 | 日志 + 规则校验 |
| 成本 | token 与调用次数 | 计量 |
| 安全 | 越权、注入触发率 | 红队测试集 |

**最有效的评测方法是"轨迹回放"**：把失败案例的完整消息序列拿出来，逐步骤看模型在哪一步判断错。这比看最终答案有用得多。

:::warn 常见坑
- 没有步数上限，遇到死循环时账单爆炸；
- 工具没有幂等设计，重试导致重复下单/重复发邮件；
- 把工具返回的原始 HTML/JSON 全塞进上下文，一次就撑爆窗口；
- 让模型自己决定"要不要执行危险操作"，正确做法是让系统决定——模型只提议，权限在系统侧。
:::
