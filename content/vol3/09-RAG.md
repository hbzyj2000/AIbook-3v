# 8　RAG：把"查得到"变成"答得准"

RAG（检索增强生成）不是"接一个向量库"，而是一条有七个环节的流水线，任何一环掉链子，最终答案都会错。这一章按流水线顺序讲。

## 8.1 七个环节

```text
① 解析 → ② 切分 → ③ 嵌入 → ④ 索引
                                    ↓
⑧ 生成 ← ⑦ 组装 ← ⑥ 重排 ← ⑤ 召回
```

每个环节的核心问题：

| 环节 | 核心问题 | 常见失误 |
| --- | --- | --- |
| 解析 | 表格、公式、图片怎么办 | PDF 解析丢结构，表格变乱码 |
| 切分 | 一块多大、怎么切 | 切断了语义、块太大稀释信号 |
| 嵌入 | 用什么模型 | 用通用模型做垂直领域 |
| 索引 | 用什么索引 | 只做向量，漏掉精确匹配 |
| 召回 | 召回多少 | 太少漏、太多噪声 |
| 重排 | 要不要精排 | 直接按向量分数取 Top-5 |
| 组装 | 怎么放进上下文 | 塞太满、没有引用、顺序随意 |

## 8.2 解析：结构化是第一步

PDF 是最难处理的格式：双栏、表格、页眉页脚、扫描件。处理建议：

- 优先用**保留结构的解析器**（能输出 Markdown/HTML 的），不要用纯文本抽取；
- 表格单独抽出，转成 Markdown 表格或"键值对"文本，不要混在段落里；
- 扫描件走 OCR，但**务必保留页码**，用于引用溯源。

## 8.3 切分：三种策略

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| 固定长度 | 按 token 数切，带重叠 | 通用基线 |
| 结构切分 | 按标题/段落/条款切 | 有明确结构的文档（合同、手册） |
| 语义切分 | 按句子嵌入的相似度断点 | 长散文、报告 |

**块大小的权衡**：块小 → 召回精准但上下文碎片化；块大 → 上下文完整但噪声多。经验起点：**300–500 token，重叠 10%–20%**。对条款类文档，按条款切分比按长度切分效果好得多。

一个常被忽略的技巧：**给每个块加上"所属文档标题 + 章节路径"作为前缀**再嵌入，能显著提升召回（块脱离上下文后语义模糊，前缀补上了语境）。

```python
def chunk_by_heading(md_text, max_tokens=400, overlap=50):
    """按标题切分，超长段落再按长度切。返回带元数据的块。"""
    blocks, cur, cur_title = [], [], ""
    for line in md_text.splitlines():
        if line.startswith("#"):
            if cur:
                blocks.append((cur_title, "\n".join(cur))); cur = []
            cur_title = line.lstrip("# ").strip()
        else:
            cur.append(line)
    if cur:
        blocks.append((cur_title, "\n".join(cur)))

    chunks = []
    for title, body in blocks:
        # 这里用字符数近似 token 数，实际请用分词器
        for i in range(0, max(len(body), 1), max_tokens - overlap):
            piece = body[i:i + max_tokens]
            chunks.append({"title": title, "text": f"[{title}]\n{piece}"})
    return chunks
```

## 8.4 嵌入与索引

嵌入模型的选择标准：**在你的领域数据上做检索评测**，不要看榜单。通用模型（如 bge-m3、e5）在通用语料好，但在法律、医疗上常常不如领域微调的小模型。

索引的三类结构：

| 结构 | 原理 | 特点 |
| --- | --- | --- |
| 扁平（Flat） | 暴力算距离 | 精确，百万级以内可接受 |
| IVF | 先聚类再在簇内搜 | 快，需要调 nprobe |
| HNSW | 多层可导航小世界图 | 快且召回高，内存占用大 |
| PQ/OPQ | 向量分段量化 | 省内存，有精度损失 |

**HNSW 是当前默认选择**：$M$（每层连接数）与 `ef_search` 控制"召回 vs 延迟"的权衡。

## 8.5 混合检索：为什么必须有 BM25

纯向量检索对**专有名词、编号、代码、缩写**很弱——这些词的语义信息少，但精确匹配需求强。所以标准做法是双路：

$$ \text{score}=\alpha\cdot\text{norm}(\text{BM25})+(1-\alpha)\cdot\text{norm}(\text{cosine}) $$

或者各召回 20 条后用 RRF（倒数排名融合）合并。工程上更常用 RRF，因为它不需要分数归一化：

$$ \text{RRF}(d)=\sum_{r\in\text{rankers}}\frac{1}{k+\text{rank}_r(d)} $$

## 8.6 重排：性价比最高的一步

召回 50 条，重排取 5 条。交叉编码器（query 与 doc 一起编码）比双塔精度高得多，代价是每个候选一次前向。50 个候选 × 200 token ≈ 10K token 的前向，在 GPU 上是几十毫秒级，**完全可接受**。

实测经验：加一层重排通常能把"答对率"提升 5–15 个点，是所有环节里性价比最高的。

## 8.7 组装：三个细节

1. **顺序**：把最相关的放在开头和结尾（模型对中间位置的注意力弱）；
2. **引用**：给每个块编号，要求模型在回答里标注来源，便于核查与追责；
3. **冲突处理**：检索到的内容互相矛盾时，提示模型"指出冲突"而不是随便选一个。

## 8.8 评估：两个正交的指标

| 指标 | 测什么 | 怎么测 |
| --- | --- | --- |
| 检索质量（Recall@k、MRR） | 有没有找到正确片段 | 人工标注 100 条 query 的正确块 |
| 生成质量（忠实度、相关性） | 回答是否基于检索内容 | 人工或 LLM 判定 |

**必须分开测**。如果检索没找到，生成再好也是错的；如果检索对了但答错，问题在提示或模型。混在一起测，你永远不知道改哪里。

:::eng 工程视角
RAG 上线后的头号问题是"答不出但看起来很自信"。三道防线：

1. 检索为空或最高分低于阈值 → 直接回答"没有找到相关资料"；
2. 强制引用：回答里每个结论都要有块编号，没有引用的句子视为不可信；
3. 抽样人工复核，把错误样本回流成新的评测集。
:::
