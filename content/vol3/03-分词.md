# 2　分词：一个被低估的成本变量

很多人把分词当成预处理细节，实际上它同时影响三件事：**上下文能装多少内容、推理要跑多少步、以及模型对什么语言/领域更擅长**。

## 2.1 BPE 到底在做什么

算法只有三步循环：

1. 把所有文本拆成字符（或字节）；
2. 统计相邻符号对的出现频率；
3. 把最高频的对合并成一个新符号，加入词表。

重复到词表达到目标大小。结果是：**高频组合（如"的""ing"）变成单个 token，低频词被拆成子词**。

```text
"lower" 出现 10 次，"lowest" 出现 5 次
第 1 轮：最高频对 "e"+"r" -> 合并为 "er"
第 2 轮："l"+"o" -> "lo"，"lo"+"w" -> "low"
最终：low 成为一个 token，"lowest" = low + est = 2 个 token
```

BPE 之后一般还要做**字节级处理**（byte-level BPE）：把字符先映射到字节，保证任何 Unicode 都能表示，不会出现"未登录词"。

## 2.2 词表大小的权衡

$$ \text{序列长度}\approx\frac{\text{字符数}}{\text{平均每 token 字符数}} $$

词表越大，平均每 token 覆盖的字符越多，序列越短。但代价是：

- 嵌入矩阵变大（$V\times d$），输出层同理，这部分参数在小模型上占比很高；
- 低频 token 的训练样本少，学不好；
- softmax 计算量随 $V$ 增长。

| 词表规模 | 典型模型 | 特点 |
| --- | --- | --- |
| 32K | LLaMA 系 | 英文效率好，中文偏差 |
| 50K–64K | 多数通用模型 | 平衡 |
| 100K+ | 多语言模型 | 多语言效率好，嵌入矩阵大 |

**中文的坑**：英文为主的词表处理中文时，一个汉字常被拆成 1–3 个 token。同样一段中文，token 数可能是英文的 1.5–2 倍——**直接导致上下文更短、成本更高**。所以中文场景优先选中文覆盖好的分词器，或干脆用中文语料重训词表（代价是要重训嵌入层）。

## 2.3 估算 token 数

没有分词器在手时的经验值（不同词表差异很大）：

| 内容类型 | 每 token 大约覆盖 |
| --- | --- |
| 英文普通文本 | 4 个字符 / 0.75 个词 |
| 中文普通文本 | 1–1.5 个汉字 |
| 代码 | 3 个字符（缩进与符号开销大） |
| 数字/JSON | 1–2 个字符（数字常被逐位拆开） |

工程做法：**用真实分词器统计你的业务语料的平均 token 数**，而不是套经验值。这一步能避免容量规划偏差 50%。

## 2.4 分词器的六个工程坑

1. **训练与推理的分词器必须完全一致**。词表差一个 token，embedding 行就错位，输出全是乱码；
2. **新增特殊 token 后要 resize 嵌入矩阵**，否则索引越界；
3. **空白与前导空格**：BPE 对空格敏感，"hello" 与 " hello" 是不同 token。拼接字符串时容易丢空格；
4. **中文全角/半角**、繁简、异体字，会被编成完全不同的 token；
5. **代码的缩进**：4 空格 vs Tab 会产生不同 token，模型对不一致的缩进很敏感；
6. **tokenizer 不是无损的**：某些控制字符会被规范化丢弃，做"原文回显"时要保留原文而不是反解码。

:::eng 工程视角
如果你在做长文档处理，**先用分词器量一遍 token 分布**：最短、中位、P95、最长。这决定了切分块大小、上下文预算、以及要不要做摘要压缩。很多人卡在"上下文超限"，根源是没有量过。
:::
