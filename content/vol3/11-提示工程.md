# 10　提示工程：有效约束与无效仪式

这一章刻意区分两类做法：**能通过对比实验证明有效**的，和**主要靠心理安慰**的。做过 A/B 的团队都知道，很多流行技巧换一个任务就不工作。

## 10.1 六条稳定有效的手段

| 手段 | 为什么有效 | 示例要点 |
| --- | --- | --- |
| 明确任务与输出格式 | 减少歧义，缩小搜索空间 | "输出 JSON，字段 a/b/c" |
| 给示例（few-shot） | 用具体例子定义"好答案"的样子 | 2–5 个覆盖不同情形 |
| 分解步骤 | 把多步推理拆成可检查的小步 | "先列出已知，再计算" |
| 提供材料 | 让模型基于给定文本而非记忆 | 引用块 + 编号 |
| 设定拒答条件 | 给"不知道"一条合法出口 | "材料中无依据时回答：未找到" |
| 约束长度与粒度 | 避免冗长和跑题 | "不超过 5 句，每句一个结论" |

这六条的共同点是：**都在减少模型需要自己猜的东西**。提示工程的本质是"接口设计"，不是"咒语"。

## 10.2 思维链：什么时候有用，什么时候没用

"让我们一步步思考"这类提示在多步算术、逻辑推理上确实有效，原因是它把隐式计算变成了显式 token，模型有更多计算预算。

但它有明确的适用边界：

- **有效**：需要多步推理、有中间量可以写出；
- **无效甚至有害**：简单任务（浪费 token）、需要直觉的任务（强行拆解反而错）、以及**要求诚实报告推理过程**的场景——模型写出的"推理"常常是事后编的，与实际决策路径不一致。

所以：**要结果可靠性，用 CoT；要可解释性，不要指望 CoT 的文本是真因**。

## 10.3 结构化输出：最工程化的部分

要求 JSON 有两种实现层次：

| 层次 | 做法 | 可靠性 |
| --- | --- | --- |
| 提示约束 | 在提示里要求 JSON 并给示例 | 中，偶有格式错 |
| JSON mode | 引擎层保证语法合法 | 高 |
| 语法约束解码 | 用 grammar/regex 约束 token 采样 | 最高，字段与枚举都可强制 |

语法约束解码的原理：在每一步把不符合当前语法状态的 token 概率置零，再做采样。**这只保证语法，不保证语义**——模型可以生成完全合法但内容错误的 JSON。

```python
# 伪代码：按语法状态过滤 logits
def constrained_logits(logits, parser_state):
    allowed = parser_state.allowed_tokens()   # 由 grammar 推导
    mask = torch.full_like(logits, -float("inf"))
    mask[allowed] = 0
    return logits + mask
```

## 10.4 上下文工程：比措辞更重要

同样一段材料，放在不同位置、不同长度，效果差异巨大。四条实证结论：

1. **首尾优于中间**（lost in the middle）。关键信息放开头或结尾；
2. **无关内容会显著降低准确率**，不是"多读点总没坏处"。宁少勿滥；
3. **结构标记有效**：用清晰的分隔符与编号，比自然语言段落好；
4. **指令放在末尾**比放在开头更容易被遵循（尤其在长上下文里）。

一个实用的模板：

```text
[角色与任务]  你是资料整理助手，只根据给定材料作答。

[材料]
<doc id="1">...</doc>
<doc id="2">...</doc>

[规则]
1. 每个结论后标注来源编号，如 [1]。
2. 材料中没有的，回答"未找到"。
3. 输出 JSON：{"answer": str, "citations": [int]}

[问题]
...
```

## 10.5 那些被高估的技巧

- **"请深呼吸""这对我的职业很重要"**：个别模型上偶有微小提升，但不稳定，跨模型不通用；
- **长篇人格设定**：对风格有影响，对能力几乎无影响，还消耗上下文；
- **堆叠大量"务必""必须""绝对"**：过度强调会让模型在边界处过度谨慎或忽略其他要求；
- **要求模型"证明自己正确"**：会诱发编造论据。

判断标准很简单：**同一批测试样本上做对比，差异是否稳定**。没有对比数据的"技巧"不值得写进生产提示。

## 10.6 提示也需要版本管理

生产提示应该像代码一样管理：

- 存版本（v1/v2），记录改动与对应指标；
- 有回归测试集，改完跑一遍；
- 关键提示的改动要走评审；
- 记录"为什么这么写"（很多提示的约束是为了修某个具体 bug，不写清楚就会被后人删掉）。

:::eng 工程视角
把提示当成**配置 + 契约**：输入输出的格式约定写在提示与后处理两侧，两边都要校验。只在一侧约束，另一侧迟早漂移。
:::
