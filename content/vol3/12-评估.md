# 11　评估与可观测：怎么知道它变好了

这一章给一套可以直接照做的评估体系：**一个私有评测集、一套分层指标、一条回归流水线**。

## 11.1 私有评测集：最重要的一件事

做法：

1. **从真实流量采样**：覆盖主要场景与长尾，至少 200 条，理想 500+；
2. **人工写出期望输出**（或标注关键要点），不是"标准答案"而是"必须包含什么、不能出现什么"；
3. **分层**：按场景分组（问答/抽取/生成/拒答），每组至少 30 条；
4. **固定版本**：评测集一旦定版就不改，新增另开 v2，否则历史对比失效。

一个评测样本的结构：

```json
{
  "id": "qa-017",
  "input": "用户原始问题",
  "context": ["检索块1", "检索块2"],
  "must_include": ["关键结论A", "来源编号"],
  "must_not": ["编造的数字", "超出材料的推断"],
  "scenario": "制度问答"
}
```

## 11.2 三层指标

| 层 | 指标 | 判定方式 |
| --- | --- | --- |
| 客观 | 格式合法率、字段完整率、引用命中率 | 规则/脚本 |
| 语义 | 要点覆盖率、事实一致性 | LLM 判定 + 抽样人工 |
| 业务 | 采纳率、人工修改率、任务完成率 | 线上埋点 |

**顺序很重要**：先保证客观指标 100%（格式错了后面的评测无意义），再看语义，最后看业务。

## 11.3 LLM-as-judge：能用，但要设计

judge 的三种用法：

| 用法 | 可靠性 | 说明 |
| --- | --- | --- |
| 逐项检查清单 | 较高 | "回答是否引用了来源？是/否" |
| 成对比较 | 较高 | "A 和 B 哪个更好"，交换顺序消偏 |
| 整体打分（1–10） | 低 | 分数不稳定，不可比 |

必须做的三件事：

1. **交换顺序**消除位置偏置；
2. **固定评分标准**（写在 judge 提示里，逐条）；
3. **与人工对齐验证**：抽 50 条人工标一遍，算一致性（Cohen's kappa）。一致性低于 0.6 就不要用 judge 做主判据。

## 11.4 回归流水线

```text
改提示/换模型/调参数
      ↓
跑评测集（离线，分钟级）
      ↓
对比基线：格式、要点覆盖、延迟、成本
      ↓
通过阈值 → 影子流量 → A/B → 全量
```

**每次改动都要跑**。这不是流程负担，而是唯一能让"这次改动是不是变好了"有答案的办法。

## 11.5 线上可观测：五个必看信号

| 信号 | 异常表现 | 说明 |
| --- | --- | --- |
| 输入长度分布 | 突然变长/变短 | 上游改版或用户行为变化 |
| 拒答率 | 突然升高 | 检索坏了或提示过严 |
| 输出长度 | 突然变长 | 模型/提示变更导致啰嗦 |
| 延迟 P99 | 升高 | 并发或上下文变长 |
| 用户反馈 | 差评关键词集中 | 需要按场景分解 |

**分布监控比准确率监控更重要**：准确率你只能抽样估计，分布变化是实时可见的先行指标。

## 11.6 失败分类学

把失败样本按原因分类，才知道往哪改：

| 类别 | 表现 | 归因 |
| --- | --- | --- |
| 检索缺失 | 材料里没有正确信息 | 切分/召回/索引 |
| 检索噪声 | 材料里有但被淹没 | 重排/上下文组装 |
| 指令误解 | 材料对但答偏 | 提示/示例 |
| 事实幻觉 | 编造材料里没有的内容 | 提示约束/模型能力 |
| 格式错误 | JSON 缺字段 | 后处理校验 |
| 过度拒答 | 明明能答却说不知道 | 提示阈值 |

统计各类占比，通常会发现**检索类问题占一半以上**——这就是"先修检索，再换模型"的依据。

:::note 要点
评估的目标不是"打个分"，而是**让每次改动都有可比较的证据**。一个 200 条的私有评测集，价值超过任何公开榜单。
:::
