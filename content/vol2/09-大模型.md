# 8　大模型：能力边界与成本结构

这一章不讲解法（解法在卷三），讲**判断**：什么时候该用大模型、用多大的、贵在哪、承诺给业务方的能力里哪些是靠不住的。

## 8.1 三段式训练范式

| 阶段 | 数据 | 目标 | 得到什么 |
| --- | --- | --- | --- |
| 预训练 | 万亿级 token 文本 | 下一个 token 预测 | 语言能力、世界知识、推理雏形 |
| 监督微调（SFT） | 数万到数百万条指令-回答 | 学会"按指令作答" | 可用性、格式遵循 |
| 对齐（RLHF/DPO） | 人类偏好对比 | 让回答更符合偏好 | 有用性、无害性、语气 |

这个范式解释了一个常见困惑：**为什么模型"知道"很多却常常答错**？因为预训练优化的是"预测下一个词"，而不是"说真话"。知识以统计关联的形式存在，不是可检索的事实库。SFT 与对齐改变的是行为风格，不能保证事实正确。

## 8.2 能力边界：四类可靠与四类不可靠

| 相对可靠 | 相对不可靠 |
| --- | --- |
| 语言改写、翻译、摘要 | 精确数值计算、多步算术 |
| 格式转换、结构化抽取 | 长链逻辑推理（超过 5–6 步） |
| 代码生成（有明确模式） | 需要外部实时信息的事实问答 |
| 按给定材料作答 | 判断"自己不知道"（校准差） |

第三行与第四行是最需要工程补偿的：前者靠工具调用（计算器、代码执行），后者靠检索与"引用出处"约束。

**关于幻觉**，需要理解它的机制而不是当成 bug：模型在生成每个 token 时做的是概率采样，流畅性与正确性由同一个目标驱动。当训练数据里"看起来合理的错误"很常见时，模型会学到"编得像"比"承认不知道"更符合分布。所以要靠外部约束（检索、引用、拒答训练），不能靠提示词根治。

## 8.3 成本结构：三笔账

### 训练账

$$ \text{训练算力}\approx 6\times N\times D $$

$N$ 是参数量，$D$ 是训练 token 数。这个 6 来自前向 2 次 + 反向 4 次浮点运算/参数/token。例如 7B 模型训 2T token：$6\times7\times10^9\times2\times10^{12}\approx8.4\times10^{22}$ FLOPs。按 A100 的 312 TFLOPS（FP16，实际利用率约 40%）折算，需要约 $6.7\times10^{5}$ GPU 小时。

### 推理账

$$ \text{每 token 算力}\approx 2N\ (\text{前向}),\qquad \text{显存}\approx \text{权重}+ \text{KV cache} $$

7B 模型 FP16 权重 14GB，加上 KV cache 与激活，单卡 24GB 可以跑；13B 需要 24GB 以上或量化；70B 需要多卡或 INT4。

### 上下文账

上下文长度不是免费的：KV cache 随序列长度线性增长，注意力计算随长度平方增长。**长上下文 = 更贵的显存 + 更慢的首 token**。这是"为什么不能无脑塞满上下文"的量化解释。

## 8.4 选型：参数规模与任务匹配

| 任务 | 建议规模 | 理由 |
| --- | --- | --- |
| 分类、抽取、改写（有标注） | 小模型微调（0.1–1B）或 BERT 类 | 精度足够、成本低一个量级 |
| 通用问答、RAG | 7–14B | 能力与成本平衡点 |
| 复杂推理、代码 | 30B 以上或调用 API | 规模对推理能力影响显著 |
| 端侧/离线 | 1–4B 量化 | 内存与功耗约束 |
| 高并发简单任务 | API 或小模型 + 缓存 | 单位成本优先 |

一个务实策略：**先用最大的可用模型做"能力上限测试"，再用小模型逼近**。如果大模型也做不好，说明问题不在模型规模，而在任务定义或数据。

## 8.5 评测的陷阱

- **数据污染**：benchmark 的题目可能出现在预训练语料里，分数虚高；
- **提示敏感**：同一个模型换一种问法，分数差 10 个点；
- **选择偏差**：只报告最好的那次运行；
- **指标与用途脱节**：MMLU 高不代表你的业务场景好。

靠谱的做法是**自建业务评测集**：从真实流量里采样 200–500 条，人工标注期望输出，形成回归测试。这个集合比任何公开榜单都有用。

:::note 要点
把大模型当"能力很强但不可靠的实习生"来用：给它明确的材料（检索）、明确的格式（结构化输出）、明确的检查（后处理校验），并保留人工复核。这个定位比"智能助手"更符合它现在的实际水平。
:::
