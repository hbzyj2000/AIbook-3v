# 10　强化学习与智能体：会决策的系统怎么搭

强化学习的数学（MDP、贝尔曼、策略梯度、PPO）在卷一第 14 章。这一章讲**它在哪里真的有用**，以及"智能体"这个被过度使用的词到底指什么。

## 10.1 强化学习的适用边界

强化学习适合同时满足三个条件的场景：

1. **有明确的奖励信号**（赢/输、成本、成功率）；
2. **可以大量试错**（仿真环境、线上有安全边界）；
3. **决策是序列的**（当前动作影响未来状态）。

不满足就优先用监督学习或规则：

| 场景 | 更适合的方法 |
| --- | --- |
| 单步决策、有标注 | 监督学习 |
| 奖励稀疏且无法仿真 | 模仿学习 / 逆强化学习 |
| 状态空间小、规则明确 | 搜索 / 动态规划 |
| 需要可解释与合规 | 规则 + 监督模型 |

## 10.2 四个真实应用方向

- **游戏与仿真**：AlphaGo、Atari、Dota——环境可无限重置，是 RL 的最佳试验场；
- **机器人控制**： sim2real 是核心难题，域随机化（随机材质、光照、质量）是常用手段；
- **推荐与广告**：把"用户反馈"当奖励，但要注意"奖励滞后"与"策略偏置"（只学到已曝光内容）；
- **调度与资源分配**：数据中心冷却、物流路径、电网调度，奖励明确且可仿真。

工业界真正赚钱的 RL 应用大多**不是端到端的**，而是"RL 优化一个局部决策 + 传统系统兜底"。这一点常被媒体叙事掩盖。

## 10.3 智能体的四个部件

把"智能体（Agent）"拆开，它必须有四件东西：

| 部件 | 作用 | 缺了会怎样 |
| --- | --- | --- |
| 感知 | 读入用户输入、环境状态 | 无法响应变化 |
| 规划 | 把目标拆成步骤 | 遇到多步任务就乱 |
| 工具 | 调用搜索、代码、API | 只能空谈，不能行动 |
| 记忆 | 保存上下文与历史结果 | 重复劳动、前后矛盾 |

一个常见的误解是"给模型加个工具调用就是 Agent"。实际上**规划与记忆才是分水岭**：能自己决定"先查什么、再算什么、什么时候停"，才算智能体。

## 10.4 三种架构范式

| 范式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| ReAct | 思考→行动→观察，循环 | 简单、可解释 | 步数多则成本高、容易绕圈 |
| Plan-and-Execute | 先出计划再执行 | 全局性好 | 计划错了全错，需要重规划 |
| 多智能体 | 角色分工（规划者/执行者/评审） | 可并行、可互相检查 | 通信成本高、易发散 |

工程上的经验是：**先用单 Agent + 少量工具，跑通再拆**。多智能体在任务确实可分解、且子任务需要不同上下文时才划算。

## 10.5 可靠性：智能体最缺的东西

智能体的失败模式与聊天模型完全不同：

- **无限循环**：反复调用同一工具。必须设最大步数与"无进展检测"；
- **工具误用**：参数格式错、调用了不该调的接口。要靠 schema 校验与权限白名单；
- **目标漂移**：中途忘了原始目标。靠显式的目标重述与状态记录；
- **错误累积**：一步错，后面全错。靠中间结果校验与可回滚。

:::eng 工程视角
把智能体当成**一个不可信的执行器**来设计：每一步的输入输出都记日志、关键动作要人工确认、工具要有权限边界与超时、失败要能回到上一个安全状态。这套思路和分布式系统的容错设计是一样的。
:::

## 10.6 与用户业务的关系

实际落地中，智能体最有价值的三类场景：

1. **重复的多步操作**（对账、报表生成、工单流转）；
2. **需要跨系统查询的问答**（把检索、数据库、API 串起来）；
3. **有明确验收标准的生成任务**（代码修改后跑测试、文案生成后过审）。

共同点是**有客观的中间校验**。没有校验的开放任务，智能体的成功率会低到不可用。
