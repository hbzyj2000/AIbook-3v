# 11　工程落地：从实验到服务

这一章是给工程背景的人写的。模型的结构再漂亮，落到线上都绕不开三件事：**能不能训得起、能不能跑得快、能不能稳得住**。

## 11.1 训练侧：四个基础设施

| 组件 | 作用 | 常见方案 |
| --- | --- | --- |
| 数据管线 | 读取、解码、增强、批处理 | WebDataset / tf.data / DALI |
| 分布式训练 | 多卡多机 | DDP（数据并行）、FSDP/ZeRO（分片）、流水并行 |
| 实验管理 | 记录超参、指标、权重 | MLflow / W&B / 自建 |
| 环境与复现 | 依赖、种子、版本 | 容器镜像 + 锁版本 |

一个常被低估的瓶颈是**数据加载**：GPU 利用率上不去，往往是 CPU 解码跟不上。诊断方法很简单——看 GPU 利用率是否周期性掉到 0，以及 `nvidia-smi` 的显存是否稳定。

## 11.2 推理优化：七种手段与收益量级

| 手段 | 收益 | 代价 | 适用 |
| --- | --- | --- | --- |
| 算子融合 | 1.2–2× | 需要编译优化 | 通用 |
| 量化（INT8/INT4） | 2–4× | 精度掉 0.5–2 点 | 通用，需校准 |
| 剪枝/稀疏 | 1.3–2× | 需要专门硬件支持才见效 | 边缘设备 |
| 批处理 | 吞吐提升数倍 | 延迟增加 | 离线/高并发 |
| KV cache 复用 | 长上下文省算力 | 占显存 | LLM 必用 |
| 蒸馏到小模型 | 3–10× | 精度损失、训练成本 | 有明确任务 |
| 投机解码 | 1.5–3× | 需要草稿模型 | LLM 生成 |

**收益量级很重要**：不要为一个 5% 的优化投入两周，也不要指望量化之后精度完全不变。

## 11.3 框架选型

| 框架 | 平台 | 特点 |
| --- | --- | --- |
| ONNX Runtime | 跨平台 | 通用、算子覆盖广、支持量化 |
| TensorRT | NVIDIA | 极致性能，需针对 GPU 编译，构建耗时 |
| OpenVINO | Intel CPU/iGPU | 英特尔平台优化好 |
| llama.cpp | CPU/GPU 混合 | LLM 友好，GGUF 量化，可纯 CPU 跑 |
| MNN / NCNN | 移动端 | 轻量、ARM 优化 |
| TVM | 通用编译 | 可定制，学习曲线陡 |

选型的判断顺序：**目标硬件 → 算子覆盖 → 量化支持 → 社区活跃度**。很多团队卡在"模型里有个自定义算子，目标框架不支持"，最后只能回退。

## 11.4 C++ 部署的完整链路

```cpp
// 1) 导出：PyTorch -> ONNX（固定输入形状，或声明动态维）
//    torch.onnx.export(model, dummy, "m.onnx", opset_version=17,
//                      input_names={"x"}, dynamic_axes={"x":{0:"batch"}})

// 2) 加载会话（一次性，耗时可到秒级）
Ort::Session session(env, "m.onnx", Ort::SessionOptions{});
// 3) 预热：跑几次空推理，触发内存分配与 kernel 选择
// 4) 推理：复用输入输出张量缓冲，避免每次分配
std::vector<float> input(1 * 3 * 224 * 224);
auto out = session.Run(Ort::RunOptions{nullptr}, names_in, &in_tensor, 1, names_out, 1);
```

四个容易踩的坑：

- **每帧新建 Session**：初始化开销远超推理本身，必须复用；
- **每帧分配内存**：用内存池或复用缓冲区，否则分配器成为瓶颈；
- **线程数没配**：`intra_op_num_threads` 设成物理核数，超线程反而拖慢；
- **输入布局不一致**：训练是 NCHW，某些引擎默认 NHWC，转置开销可能比推理还大。

## 11.5 服务化：三个必须有的机制

1. **动态批处理**：把多个请求拼成一个 batch，用微小延迟换数倍吞吐。LLM 场景用连续批处理（continuous batching），请求完成即释放槽位；
2. **降级与限流**：GPU 打满时返回缓存结果或简化模型，避免雪崩；
3. **可观测**：记录 QPS、P50/P99 延迟、GPU 利用率、显存、错误率、以及**输入分布**（长度、语言、类型）。

## 11.6 成本模型：一个能算的公式

$$ \text{单位成本}=\frac{\text{GPU 小时单价}\times\text{占用时长}}{\text{请求数}}+\text{存储与网络} $$

举例：一张 A10（约 1 美元/小时）跑 7B INT4 模型，吞吐 20 req/s，则每请求算力成本约 $1/72000\approx0.000014$ 美元，可以忽略；但如果每次请求要 4 秒、吞吐只有 0.25 req/s，成本就变成 0.0011 美元/次，一天十万次就是 110 美元。**延迟直接决定成本**，这是很多人忽略的账。

## 11.7 上线检查清单

- [ ] 模型版本与权重有唯一标识，可回滚
- [ ] 输入校验（长度、类型、编码）与超时
- [ ] 输出后处理与格式校验
- [ ] P99 延迟满足 SLA，且有压测数据
- [ ] 降级策略明确（缓存/小模型/排队）
- [ ] 日志记录输入摘要、输出、耗时（注意隐私）
- [ ] 分布监控与报警阈值
- [ ] 灰度发布与 A/B 能力

:::eng 工程视角
你的 C++ 背景在这里是优势：**能看懂算子、能定位内存与线程问题、能做零拷贝与批处理**。很多 AI 工程师停在 Python 层，性能和稳定性的优化空间就在这里。把 ONNX/TensorRT 的 profile 打开，看每一层的耗时，通常能发现 20–40% 的浪费。

## 压测怎么做才有意义

压测不是"打满 QPS 看会不会挂"，而是要找到**性能曲线的拐点**。

| 阶段 | 做什么 | 看什么 |
| --- | --- | --- |
| 单请求基线 | 一次请求，冷启动与热启动各测 | 冷启动耗时（模型加载） |
| 阶梯加压 | 并发 1→2→4→8→…→128 | 吞吐是否线性增长、延迟何时起飞 |
| 拐点确认 | 在吞吐饱和点附近细测 | 排队长度、GPU 利用率 |
| 长稳测试 | 拐点 70% 负载跑 2 小时 | 内存泄漏、显存碎片 |
| 异常注入 | 杀一个 worker、注入超时 | 降级是否生效 |

三个常见误判：

- **只看平均延迟**：P99 才是用户感知的；
- **忽略预热**：前 100 个请求慢是因为 kernel 未编译、缓存未填充；
- **用合成数据**：输入长度分布与线上不同，结果没有参考价值。

压测结论要写成一句可执行的话，例如"单卡在 8 并发下吞吐 22 req/s，P99 延迟 1.8s，超过 12 并发延迟翻倍"，而不是一张图。
