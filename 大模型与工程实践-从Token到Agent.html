0　导读：一条请求的完整链路

把一次请求拆成七个阶段，每个阶段对应一个可优化的点。

导读　·　约 1134 字　·　3 分钟

这一卷的组织方式很具体：跟着一次推理请求往下走。从字符串变成 token，进模型，经过几十层注意力与前馈，出 logits，被采样成下一个 token，再循环；如果接了检索，还要在前面插入一次向量查询；如果接了工具，还要在外面套一层决策循环。

每经过一个环节，都会有一笔账要算——显存、带宽、延迟、成本。这一卷的重点就是把这四笔账算清楚，让你能判断瓶颈在哪，而不是盲调参数。

1.10.1 七个阶段

阶段输入 → 输出主要成本可优化点
① 预处理文本 → token IDCPU，可忽略缓存、批处理
② 嵌入ID → 向量一次查表无
③ 编码（prefill）全部 prompt → KV算力密集FlashAttention、并行
④ 解码（decode）逐 token 生成带宽密集KV cache、批处理、量化
⑤ 采样logits → 下一个 token可忽略温度/top-p
⑥ 后处理token → 文本可忽略流式输出
⑦ 编排检索、工具、重试网络与串行并行、缓存、路由

关键认识：prefill 是算力密集，decode 是带宽密集。 这两个阶段的瓶颈完全不同，所以优化手段也不同——批处理对 decode 收益极大，对 prefill 收益有限；量化对两者都有效，但影响不同。

1.20.2 三个必须先算的数

进入细节之前，先把三个量级建立起来：

  1. 权重显存：N 参数、b 字节/参数 → N b 字节。7B FP16 = 14GB，INT4 ≈ 3.5GB；
  2. KV cache 显存：2 \times L \times S \times H \times B \times b 字节（K 和 V，每层 S\times H）；
  3. 每 token 计算量：前向约 2N FLOPs，训练约 6N（含反向）。
KV cache 显存账本改层数、隐藏维、序列长度与并发，看推理显存花在哪

上面这个账本可以直接玩：把并发从 8 提到 64，你会看到 KV cache 迅速超过权重，成为显存的主要占用——这是所有推理优化的起点。

1　Transformer 精讲：从配置到形状到账本

把配置读成形状、把形状读成参数量，再把参数量读成显存与算力。

架构　·　约 2498 字　·　7 分钟

原理在卷一第 12 章推导过。这一章做三件事：读懂一份模型配置、追踪一次前向的全部形状、算出它的参数与显存。这三件事会了，你看任何新模型架构都不会慌。

2.11.1 读懂配置

拿一个典型的 7B 配置举例：

text
hidden_size          4096     # d_model，残差流的宽度
num_hidden_layers    32       # 层数
num_attention_heads  32       # 头数
head_dim             128      # = hidden_size / num_attention_heads
intermediate_size    11008    # FFN 中间维，约 2.7 倍 d_model
vocab_size           32000
max_position         4096

四个数字之间的关系记住：每头维度 = 隐藏维 / 头数。头数增加则每头维度减小。现代模型（LLaMA 系）常用 head_dim=128 固定，让头数与隐藏维解耦。

2.21.2 参数量手算

每层的参数量：

部件公式7B 配置下的值
Q、K、V 投影3 × 隐藏维平方（MHA）3 × 16.8M = 50.3M
输出投影隐藏维平方16.8M
FFN（SwiGLU，3 个矩阵）3 × 隐藏维 × 中间维3 × 4096 × 11008 ≈ 135M
两个 RMSNorm2 × 隐藏维8K
每层合计≈ 202M

32 层约 6.5B，加上嵌入（32000\times4096\approx131M，通常与输出层共享权重）约 6.7B。这就是"7B"的来源。

记住这个比例：FFN 占每层参数的三分之二。 所以"加宽 FFN"和"加层"是两种不同性质的扩容，前者提升每层的特征变换能力，后者提升组合深度。

2.31.3 一次前向的形状追踪

下面这段是教学用的简化实现，注释里标了每一步的形状。跑一遍，形状就长在脑子里了。

python
import torch, torch.nn as nn, math

B, T, D, H, F = 2, 1024, 4096, 32, 11008
dh = D // H                       # 128

class Block(nn.Module):
    def __init__(self):
        super().__init__()
        self.ln1 = nn.RMSNorm(D)
        self.wq = nn.Linear(D, D, bias=False)
        self.wk = nn.Linear(D, D, bias=False)
        self.wv = nn.Linear(D, D, bias=False)
        self.wo = nn.Linear(D, D, bias=False)
        self.ln2 = nn.RMSNorm(D)
        self.w1 = nn.Linear(D, F, bias=False)   # SwiGLU 的 gate
        self.w3 = nn.Linear(D, F, bias=False)   # SwiGLU 的 up
        self.w2 = nn.Linear(F, D, bias=False)   # down

    def forward(self, x):                        # (B,T,D)
        h = self.ln1(x)
        q = self.wq(h).view(B, T, H, dh).transpose(1, 2)   # (B,H,T,dh)
        k = self.wk(h).view(B, T, H, dh).transpose(1, 2)
        v = self.wv(h).view(B, T, H, dh).transpose(1, 2)
        att = (q @ k.transpose(-1, -2)) / math.sqrt(dh)    # (B,H,T,T)
        att = att.masked_fill(causal_mask, -torch.inf)
        att = att.softmax(dim=-1)
        o = (att @ v).transpose(1, 2).reshape(B, T, D)      # (B,T,D)
        x = x + self.wo(o)
        h = self.ln2(x)
        x = x + self.w2(torch.silu(self.w1(h)) * self.w3(h))  # (B,T,D)
        return x

三个值得停下来看的地方：

  • view(B,T,H,dh).transpose(1,2)：把"隐藏维"拆成"头数 × 每头维度"，再把头提到 batch 维旁边。这是所有实现里最容易写错的一步；
  • att @ v 之后再 transpose 回 (B,T,D)：多头的输出要拼回去；
  • SwiGLU 有两个上投影一个下投影：w_1 做门控，w_3 提供值，相乘后由 w_2 降维。相比传统 FFN（两个矩阵），参数多 50%。

2.41.4 每个子层在做什么

子层功能直觉工程要点
自注意力位置之间交换信息（"我该看谁"）复杂度与序列长平方成正比，是长上下文瓶颈
FFN每个位置独立做特征变换参数占三分之二，可按位置并行
残差保证梯度直通深层需要缩放初始化
归一化稳定各层尺度Pre-LN 是现代默认

一个流传很广的类比：注意力是"通信"，FFN 是"计算"。注意力让 token 之间传递信息，FFN 把信息加工。这个类比在分析 MoE（把 FFN 换成多个专家）时特别有用——MoE 本质是"扩大计算容量而不增加通信量"。

2.51.5 现代变体：四个必知改动

改动作用代价
RoPE相对位置编码，支持长度外推需要配合插值方法才能真的外推
RMSNorm省掉均值计算数值上略不同，效果基本持平
SwiGLU门控 FFN，效果更好参数多 50%
GQA / MQA多个查询头共享一组 KVKV cache 减少数倍，质量略降

GQA 值得重点理解：标准 MHA 里每个头都有自己的 K、V，KV cache 大小与头数成正比。GQA 让 q 个查询头共享 1 组 KV（例如 32 个 Q 头共享 8 组 KV），KV cache 直接降到四分之一。这是长上下文与高并发场景的关键优化，几乎所有新模型都用它。

\text{KV 大小}=2\times L\times S\times H_{kv}\times d_{head}\times B\times b

注意这里的 H_{kv} 是 KV 头数，不是查询头数。看模型配置时一定确认 num_key_value_heads，它直接决定你的显存能撑多少并发。

2.61.6 Pre-LN 与 Post-LN

text
Post-LN:  x = LN(x + Attn(x))     # 原始论文
Pre-LN:   x = x + Attn(LN(x))     # 现代主流

Pre-LN 的好处是残差路径上没有归一化，梯度可以无损地直通，深层训练更稳，不需要精细的 warmup。代价是输出范数会随层数增长，所以最后要加一个 final norm。

常见坑
  • 加载别人的权重却用了不同的 Norm 位置，loss 会异常高——这不是训练问题，是结构不匹配；
  • 注意力实现里忘了因果掩码，训练时 loss 会异常低（因为看到了答案），推理时完全错乱。这是最隐蔽的一类 bug；
  • 开了 flash attention 后某些自定义掩码不被支持，会静默回退到慢速实现，性能莫名下降。

2　分词：一个被低估的成本变量

词表大小决定序列长度，序列长度决定成本——分词是一个被严重低估的经济决策。

数据　·　约 1141 字　·　3 分钟

很多人把分词当成预处理细节，实际上它同时影响三件事：上下文能装多少内容、推理要跑多少步、以及模型对什么语言/领域更擅长。

3.12.1 BPE 到底在做什么

算法只有三步循环：

  1. 把所有文本拆成字符（或字节）；
  2. 统计相邻符号对的出现频率；
  3. 把最高频的对合并成一个新符号，加入词表。

重复到词表达到目标大小。结果是：高频组合（如"的""ing"）变成单个 token，低频词被拆成子词。

text
"lower" 出现 10 次，"lowest" 出现 5 次
第 1 轮：最高频对 "e"+"r" -> 合并为 "er"
第 2 轮："l"+"o" -> "lo"，"lo"+"w" -> "low"
最终：low 成为一个 token，"lowest" = low + est = 2 个 token

BPE 之后一般还要做字节级处理（byte-level BPE）：把字符先映射到字节，保证任何 Unicode 都能表示，不会出现"未登录词"。

3.22.2 词表大小的权衡

\text{序列长度}\approx\frac{\text{字符数}}{\text{平均每 token 字符数}}

词表越大，平均每 token 覆盖的字符越多，序列越短。但代价是：

  • 嵌入矩阵变大（V\times d），输出层同理，这部分参数在小模型上占比很高；
  • 低频 token 的训练样本少，学不好；
  • softmax 计算量随 V 增长。
词表规模典型模型特点
32KLLaMA 系英文效率好，中文偏差
50K–64K多数通用模型平衡
100K+多语言模型多语言效率好，嵌入矩阵大

中文的坑：英文为主的词表处理中文时，一个汉字常被拆成 1–3 个 token。同样一段中文，token 数可能是英文的 1.5–2 倍——直接导致上下文更短、成本更高。所以中文场景优先选中文覆盖好的分词器，或干脆用中文语料重训词表（代价是要重训嵌入层）。

3.32.3 估算 token 数

没有分词器在手时的经验值（不同词表差异很大）：

内容类型每 token 大约覆盖
英文普通文本4 个字符 / 0.75 个词
中文普通文本1–1.5 个汉字
代码3 个字符（缩进与符号开销大）
数字/JSON1–2 个字符（数字常被逐位拆开）

工程做法：用真实分词器统计你的业务语料的平均 token 数，而不是套经验值。这一步能避免容量规划偏差 50%。

3.42.4 分词器的六个工程坑

  1. 训练与推理的分词器必须完全一致。词表差一个 token，embedding 行就错位，输出全是乱码；
  2. 新增特殊 token 后要 resize 嵌入矩阵，否则索引越界；
  3. 空白与前导空格：BPE 对空格敏感，"hello" 与 " hello" 是不同 token。拼接字符串时容易丢空格；
  4. 中文全角/半角、繁简、异体字，会被编成完全不同的 token；
  5. 代码的缩进：4 空格 vs Tab 会产生不同 token，模型对不一致的缩进很敏感；
  6. tokenizer 不是无损的：某些控制字符会被规范化丢弃，做"原文回显"时要保留原文而不是反解码。
工程视角

如果你在做长文档处理，先用分词器量一遍 token 分布：最短、中位、P95、最长。这决定了切分块大小、上下文预算、以及要不要做摘要压缩。很多人卡在"上下文超限"，根源是没有量过。

3　预训练：数据、并行与那笔算力账

预训练的成本几乎全在"数据 × 参数 × 并行效率"这三项上。

训练　·　约 1551 字　·　4 分钟

预训练是大模型唯一"从零造能力"的阶段。它的工程量级远大于算法创新：90% 的工作是数据与基础设施。

4.13.1 数据：四道工序

工序做什么不做的后果
抽取从网页/PDF/代码库取正文混入导航栏、广告，学出噪声
质量过滤分类器打分、规则过滤低质内容拉低整体能力
去重精确 + 近似（MinHash）模型背诵训练集，评测虚高
配比按领域调权重（代码/数学/多语）能力结构失衡

去重比想象中重要：重复样本会让模型在这部分数据上过拟合，同时降低多样性。"重复 epoch"在小数据上可以，在大规模预训练里是有害的——这也是为什么缩放定律的经验公式都假设"每个 token 只训一次左右"。

4.23.2 训练的算力账

C\approx 6\,N\,D

N 是参数量，D 是训练 token 数。6 = 前向 2 + 反向 4（每个参数每个 token 的浮点运算）。举例：

  • 7B 模型、2T token：C\approx 6\times7\times10^9\times2\times10^{12}=8.4\times10^{22} FLOPs；
  • 按 A100 的 FP16 稠密算力 312 TFLOPS、实际 MFU（模型算力利用率）40% 计，有效算力 125 TFLOPS；
  • 需要 8.4\times10^{22}/1.25\times10^{14}\approx6.7\times10^{8} 秒·卡，约 21 万 GPU 小时，即 100 张 A100 跑 87 天。

MFU 是衡量训练效率的核心指标，大模型训练通常在 35%–55% 之间。低于 30% 说明有明显的通信或数据瓶颈。

4.33.3 四种并行

并行切什么通信量适用
数据并行（DP）切 batch梯度全归约，量大模型能放进单卡
张量并行（TP）切单层内的矩阵每层都要通信，延迟敏感单机多卡（NVLink）
流水并行（PP）切层只在边界传激活，但有气泡多机
专家并行（EP）切 MoE 专家all-to-all，复杂超大 MoE

实践中通常组合使用：TP 在机内、PP 跨机、DP 在最外层。再加上 ZeRO/FSDP 把优化器状态、梯度、参数分片，才能把百亿参数塞进有限显存。

4.43.4 显存账本：百亿参数怎么放

以 Adam + FP16 混合精度训练 N 参数为例：

项每参数字节7B 模型
FP16 权重214 GB
FP16 梯度214 GB
FP32 主权重428 GB
Adam 一阶矩428 GB
Adam 二阶矩428 GB
合计（不含激活）16112 GB

激活值另算，与 batch、序列长、层数成正比。所以"7B 模型需要 112GB 以上的显存"，单张 80GB 卡不够——必须分片。这就是 FSDP/ZeRO 存在的唯一理由。

4.53.5 稳定性：loss spike 怎么处理

大模型训练常见"loss 突然跳升"（loss spike）。处理顺序：

  1. 回滚到 spike 前的 checkpoint，跳过那段数据；
  2. 降低学习率，或延长 warmup；
  3. 检查是否有异常数据批次（超长、乱码、重复）；
  4. 加入梯度裁剪（通常 1.0）与 z-loss（惩罚 logits 过大）；
  5. 若频繁发生，考虑更小的 batch 或更强的归一化。

有些团队会在 spike 后动态调低 lr 并逐步恢复，这是经验做法，没有理论最优。

4.63.6 缩放定律：该给模型多少数据

经验规律（Chinchilla 一派的结论）：在固定算力下，参数量与 token 数应大致同比例增长，约每个参数配 20 个 token。这纠正了早期"只堆参数"的做法——一个 70B 模型只训 300B token，不如 7B 训 1.4T token。

模型规模建议 token 数（按 20:1）说明
1B20B小模型可以更多轮
7B140B实际常训到 1–2T（超配，收益递减但仍有）
70B1.4T接近当前主流配置

注意"超配"是常见做法：推理成本由参数量决定，训练成本由 token 数决定。为了让推理便宜，业界倾向"小模型 + 大量数据"。

常见坑
  • 用 6ND 估算时忘了考虑注意力部分的额外开销，长序列下误差可达 20%；
  • MFU 算出来很高但吞吐上不去，通常是数据管线成了瓶颈（GPU 在等 batch）；
  • 只做精确去重不做近似去重，仍会有大量近重复样本残留，评测分数虚高。

4　微调：LoRA、数据构造与遗忘

微调不是"再训练一遍"，而是"用少量数据改变行为，同时别把已有能力弄坏"。

训练　·　约 1519 字　·　4 分钟

先明确一个判断：大多数"模型不懂我们业务"的问题，靠微调解决不了，靠检索能解决。 微调擅长的是改变行为方式（格式、语气、判断标准），不擅长注入事实知识。

5.14.1 SFT 的目标与数据

监督微调就是标准的下一 token 预测，只是只对"回答部分"计损失：

python

labels[:, :prompt_len] = -100        # -100 会被 CrossEntropy 忽略

数据构造的四条经验：

  1. 多样性比数量重要。500 条覆盖 50 种任务类型，胜于 5000 条同一模板；
  2. 长度分布要覆盖。全训短回答，上线后长回答会崩；
  3. 包含"拒答"样本。只训"知无不言"，模型学不会说"我不知道"；
  4. 格式严格一致。训练时的分隔符、角色标记必须与推理时完全相同。

5.24.2 LoRA：为什么小增量够用

LoRA 冻结原权重 W，只学一个低秩增量：

W' = W + \frac{\alpha}{r}BA,\qquad B\in\mathbb{R}^{d\times r},\ A\in\mathbb{R}^{r\times k},\ r\ll \min(d,k)

参数量从 d k 降到 r(d+k)。r=8、d=k=4096 时，从 16.8M 降到 65K，约 1/256。

两个超参：

  • r（秩）：控制容量。任务越"新"，秩要越大。经验：格式调整 4–8，风格迁移 8–16，新任务学习 16–64；
  • \alpha（缩放）：实际增量是 \frac{\alpha}{r}BA。常见做法是 \alpha=2r，这样改 r 时有效学习率不变。

target modules 的选择比 r 更影响效果：至少覆盖 q_proj、v_proj，效果不够再加 k_proj、o_proj、以及 FFN 的三个投影。全加会显著增加可训练参数，但通常也显著提升效果。

5.34.3 QLoRA：把基座压到 4bit 再训

QLoRA 三步：

  1. NF4 量化：把权重压到 4bit，用分位数量化表（对正态分布最优）；
  2. 双重量化：对量化常数再量化一次，进一步省显存；
  3. 分页优化器：优化器状态在显存不足时换出到 CPU。

效果：7B 模型微调的显存需求从约 60GB 降到约 12GB，单张消费级卡可跑。代价是训练速度慢 20%–40%。

关键细节：LoRA 的增量始终在 FP16/BF16 上计算，所以量化只影响基座的前向，不损梯度的精度。这是它能保持效果的原因。

5.64.6 蒸馏：另一种"变小"的路径

如果目标是"用更小的模型做同样的事"，蒸馏往往比微调更有效：用大模型生成回答，让小模型学。关键是学软标签（完整分布）而不只是硬答案：

L=(1-\lambda)\,L_{\text{CE}}(y,\hat y)+\lambda\,T^2\,D_{\mathrm{KL}}\big(p_{\text{teacher}}^{(T)}\,\|\,p_{\text{student}}^{(T)}\big)

温度 T 用来"软化"分布，让学生看到类间关系。这套方法在小模型追赶大模型上非常有效，代价是要有足够的大模型生成数据。

5　对齐：RLHF、DPO 与可验证奖励

从奖励模型到 DPO：对齐的本质是"在保住语言能力的前提下，改变行为偏好"。

训练　·　约 1043 字　·　3 分钟

SFT 让模型"会答题"，对齐让它"答得让人满意"。两者的差别在于：SFT 学的是"标准答案长什么样"，对齐学的是"在两个都不错的回答里，人更喜欢哪个"。

6.15.1 RLHF 的三段流程

  1. 收集偏好数据：同一个 prompt 采样多个回答，让人标注哪个更好（成对比较比打分更可靠）；
  2. 训练奖励模型：输入 (prompt, response)，输出一个标量分数，用 Bradley-Terry 模型：
P(y_w\succ y_l)=\sigma\big(r_\phi(x,y_w)-r_\phi(x,y_l)\big)

损失就是 -\log\sigma(r_w-r_l)。注意它只约束"差值"，不约束绝对分数；

  1. 用 PPO 优化策略，目标为
\max_\pi\ \mathbb{E}\big[r_\phi(x,y)\big]-\beta\,D_{\mathrm{KL}}\big(\pi\|\pi_{\text{ref}}\big)

\pi_{\text{ref}} 是 SFT 后的模型。KL 项的作用是防止策略跑偏：奖励模型只在训练分布附近可靠，跑远了它给的高分没有意义（这就是 reward hacking）。

6.25.2 DPO：把两步合成一步

DPO 的推导很漂亮，值得跟一遍。带 KL 约束的最优策略有闭式解：

\pi^*(y\mid x)=\frac{1}{Z(x)}\pi_{\text{ref}}(y\mid x)\exp\!\Big(\frac{r(x,y)}{\beta}\Big)

反解出奖励：

r(x,y)=\beta\log\frac{\pi^*(y\mid x)}{\pi_{\text{ref}}(y\mid x)}+\beta\log Z(x)

把它代回 Bradley-Terry 的损失，Z(x) 在差值里消掉了，于是只需优化策略本身：

L_{\text{DPO}}=-\log\sigma\Big(\beta\log\frac{\pi_\theta(y_w\mid x)}{\pi_{\text{ref}}(y_w\mid x)}-\beta\log\frac{\pi_\theta(y_l\mid x)}{\pi_{\text{ref}}(y_l\mid x)}\Big)

这个式子的含义：让"好回答"相对参考模型的概率提升，比"坏回答"提升得更多。没有奖励模型、没有采样循环，就是一个分类损失，训练稳定得多。

维度RLHF（PPO）DPO
需要奖励模型是否
训练稳定性差（需调 KL、裁剪）好
显存4 个模型（策略/参考/奖励/价值）2 个模型
上限更高（可在线探索）受偏好数据限制
适合大规模对齐中小规模、快速迭代

6.35.3 可验证奖励：数学与代码的特殊路径

数学题有标准答案，代码有单元测试。这类任务可以用规则化奖励（答案对错、测试通过率），不需要人类标注，也不怕奖励模型被钻空子。

代表方法是 GRPO（Group Relative Policy Optimization）：对同一个问题采样一组回答，用组内均值做基线，省掉价值网络：

A_i=\frac{r_i-\mathrm{mean}(r_{1..G})}{\mathrm{std}(r_{1..G})},\qquad L=-\sum_i \min\big(\rho_i A_i,\ \mathrm{clip}(\rho_i,1\pm\epsilon)A_i\big)

组内归一化的好处是方差小、不需要额外模型，所以在数学/代码强化训练里很流行。

注意"可验证"的边界：只有答案能被自动判定的任务适用。开放写作、咨询建议无法用规则验证，只能回到偏好数据。

6.45.4 奖励黑客：对齐里最真实的风险

模型会找到"拿高分但不满足真实意图"的路径：

  • 长度作弊：奖励模型偏好长回答 → 模型越写越长；
  • 格式作弊：偏好结构化输出 → 到处加小标题；
  • 迎合作弊：学会说用户爱听的话，而不是对的答案。

三种缓解：

  1. 奖励模型集成：多个奖励模型取平均，降低单一偏好被利用的可能；
  2. KL 约束加强：\beta 调大，限制偏离；
  3. 定期人工抽检：自动指标看不出"讨好型废话"。
常见坑
  • DPO 的 \beta 太小，模型会过度优化偏好，语言能力明显退化；\beta 太大则学不到东西。常见起点 0.1；
  • DPO 只在"选中的回答"上训练，容易把"没选中的"学成绝对错误，导致过度自信。可以用 IPO 等变体缓解；
  • 偏好数据里存在标注者偏见（偏好更长、更详细），会被模型完整继承。数据清洗比算法更重要。

6　推理与解码：把生成做快

解码阶段的瓶颈是显存带宽，不是算力——这决定了所有推理优化都在"少读内存"上做文章。

推理　·　约 1935 字　·　5 分钟

生成是一个 token 一个 token 吐出来的过程。这一章解释为什么它慢、以及六种加速手段各自在解决什么。

7.16.1 采样策略

策略做法适用
贪心每步取最大概率确定性任务（抽取、代码）
束搜索保留 k 条候选路径翻译（但现代 LLM 少用）
温度采样logits 除以 T 后 softmax通用，控制随机性
top-k只在前 k 个里采样抑制长尾垃圾 token
top-p（核采样）累积概率到 p 的最小集合更自适应，常用
min-p概率低于最大值的 p 倍就截断高温下比 top-p 稳
重复惩罚降低已出现 token 的 logits缓解循环复读

经验配置：抽取/代码用 T=0；创意写作用 T=0.8–1.0 + top_p=0.9；需要多样性但不想胡说，加 min-p。

Softmax 温度实验台调 logits 与温度，看概率分布怎么变尖或变平

温度不只是"随机程度"，它改变的是分布的熵。T 很低时几乎等价贪心，T 很高时连低概率 token 都有机会——这既带来创造力，也带来事实性下降。

7.26.2 为什么 decode 慢：一次只出一个 token

生成第 t 个 token 时，模型要做一次完整前向，但只用到最后一行的输出。也就是说，你付出了全部权重的读取成本（7B FP16 约 14GB），只产出了 1 个 token。

\text{decode 的理论下限}=\frac{\text{权重字节}}{\text{显存带宽}}

A10 的带宽约 600 GB/s，14GB 权重 → 每 token 至少 23ms，即约 43 tok/s。这就是单请求的物理上限，再怎么优化算子也难以突破。想更快只有三条路：量化（减少字节）、批处理（一次读权重服务多个请求）、投机解码（一次前向出多个 token）。

7.36.3 KV cache：不存就重复算

自回归生成时，第 t 步的注意力需要前面所有 token 的 K、V。如果每步都重算，总计算量是 O(T^3)；缓存下来后是 O(T^2)。

\text{KV 大小}=2\times L\times S\times H_{kv}\times d_{head}\times B\times b

7B、32 层、8 个 KV 头、128 维、FP16、序列 4096：2\times32\times4096\times8\times128\times2\approx537MB/序列。8 路并发就是 4.3GB，还没算权重。这就是并发上不去的直接原因。

前缀缓存（prefix caching）：如果多个请求共享同一段前缀（系统提示、few-shot 示例、同一文档），这部分 KV 可以复用。多轮对话里尤其有效——每一轮都能复用之前的对话 KV。

7.46.4 批处理：连续批处理是关键

方式做法问题
静态批攒够一批一起跑，全部完成才返回短请求等长请求，利用率低
连续批（continuous batching）每个 step 检查，完成的退出、新来的插入实现复杂，需要分页管理 KV
PagedAttentionKV cache 按页分配，不要求连续显存碎片大幅减少

PagedAttention 的贡献更像操作系统：把 KV cache 切成固定大小的块，用页表映射，于是不同序列的 KV 可以交错存放，显存利用率从 20%–40% 提到 90% 以上。vLLM 就是靠这个把吞吐提升数倍。

7.66.6 投机解码：用便宜模型猜，用大模型验

思路：用一个小的草稿模型连续猜 k 个 token，再让大模型一次前向并行验证。被接受的 token 直接采用，第一个被拒绝的位置之后重新采样。

\text{加速比}\approx\frac{1}{1-\alpha}\ \text{（}\alpha\ \text{为接受率）}

接受率取决于草稿模型与目标模型的一致性：同族的小模型效果最好（如 1B 猜 7B）。加速通常 1.5–3 倍，不改变输出分布（有严格的接受-拒绝校正）。

7　长上下文：三个瓶颈与各自的解法

长上下文的三个瓶颈：注意力平方、KV 线性增长、位置编码外推。

推理　·　约 968 字　·　3 分钟

"支持 128K 上下文"是营销词，实际可用长度往往短得多。这一章把三个限制拆开，你就能判断一个模型的"长上下文"到底有多实。

8.17.1 瓶颈一：注意力的平方复杂度

\text{注意力计算}=O(T^2 d),\qquad \text{注意力显存}=O(T^2)\ \text{（若不融合）}

标准实现要把 T\times T 的分数矩阵写进显存。T=32768、32 头、FP16 时，单个头的分数矩阵就是 2GB，32 个头直接爆。

FlashAttention 的解法：不把完整的 T\times T 写回显存，而是分块（tiling）计算，边算边归一化（在线 softmax）。它把显存从 O(T^2) 降到 O(T)，速度提升 2–4 倍。注意它优化的是 IO，不是计算量——计算仍是平方级，只是不再受显存带宽限制。

\text{在线 softmax：维护 running max 与 running sum，分块累积}

8.27.2 瓶颈二：KV cache 线性增长

\text{KV}=2LSH_{kv}d_{head}Bb

序列翻倍，KV 翻倍。128K 上下文的 7B 模型，单序列 KV 就可能超过 16GB。缓解手段：

手段做法代价
GQA/MQA减少 KV 头数质量略降
KV 量化FP16 → INT8长文精度损失
滑动窗口只保留最近 N 个 token丢失远期信息
稀疏注意力只算部分位置对实现复杂
分层压缩老 token 的 KV 降维/合并需要训练适配

滑动窗口 + 全局 token 是常见折中：局部窗口保证细节，少量全局位置保证长程依赖。

8.37.3 瓶颈三：位置编码外推

模型在 4K 长度上训练，直接喂 32K 会崩——不是显存问题，是位置编码分布外。三种解法：

  • 位置插值（PI）：把超长位置线性压缩回训练范围，pos' = pos\cdot\frac{L_{\text{train}}}{L_{\text{target}}}。简单，但需要少量微调恢复；
  • NTK-aware 插值：按频率分层缩放，低频插值、高频保持，减少高频细节损失；
  • YaRN：结合频率缩放与注意力温度调整，在长文上 perplexity 明显更好。

RoPE 的旋转特性让这些方法可行：内积只依赖相对位置，所以"压缩位置轴"不会破坏相对关系，只是分辨率变粗。

常见坑
  • "支持 128K"通常指能塞进去，不代表能用好。多数模型在超过训练长度 4 倍后，检索准确率明显下降（"lost in the middle"：中间位置的信息最容易被忽略）；
  • 长上下文不是免费的：TTFT 随长度线性增长，prefill 一次 128K 可能就要几秒；
  • 把长文档全塞进去，往往不如"检索出相关片段"效果好。上下文工程 > 上下文长度。

8.47.4 一条实用判断

遇到"要不要上长上下文"的问题，按这个顺序决策：

  1. 能否用检索把输入压到 4K–8K？能，优先检索（更便宜、更准）；
  2. 必须全量输入（如整篇合同审阅）？用长上下文模型，同时做分段摘要 + 关键段召回的双路；
  3. 需要跨文档推理？考虑"先抽取结构化信息，再在结构化数据上推理"，比让模型读全文可靠。

结论：长上下文是一种能力，不是一种策略。 能用检索解决的，不要用长度硬扛。

8　RAG：把"查得到"变成"答得准"

检索质量决定回答上限：RAG 的 90% 问题出在切分与召回，不在生成。

应用　·　约 1988 字　·　5 分钟

RAG（检索增强生成）不是"接一个向量库"，而是一条有七个环节的流水线，任何一环掉链子，最终答案都会错。这一章按流水线顺序讲。

9.18.1 七个环节

text
① 解析 → ② 切分 → ③ 嵌入 → ④ 索引
                                    ↓
⑧ 生成 ← ⑦ 组装 ← ⑥ 重排 ← ⑤ 召回

每个环节的核心问题：

环节核心问题常见失误
解析表格、公式、图片怎么办PDF 解析丢结构，表格变乱码

9.28.2 解析：结构化是第一步

PDF 是最难处理的格式：双栏、表格、页眉页脚、扫描件。处理建议：

  • 优先用保留结构的解析器（能输出 Markdown/HTML 的），不要用纯文本抽取；
  • 表格单独抽出，转成 Markdown 表格或"键值对"文本，不要混在段落里；
  • 扫描件走 OCR，但务必保留页码，用于引用溯源。

9.38.3 切分：三种策略

策略做法适用
固定长度按 token 数切，带重叠通用基线
结构切分按标题/段落/条款切有明确结构的文档（合同、手册）
语义切分按句子嵌入的相似度断点长散文、报告

块大小的权衡：块小 → 召回精准但上下文碎片化；块大 → 上下文完整但噪声多。经验起点：300–500 token，重叠 10%–20%。对条款类文档，按条款切分比按长度切分效果好得多。

一个常被忽略的技巧：给每个块加上"所属文档标题 + 章节路径"作为前缀再嵌入，能显著提升召回（块脱离上下文后语义模糊，前缀补上了语境）。

python
def chunk_by_heading(md_text, max_tokens=400, overlap=50):
    """按标题切分，超长段落再按长度切。返回带元数据的块。"""
    blocks, cur, cur_title = [], [], ""
    for line in md_text.splitlines():
        if line.startswith("#"):
            if cur:
                blocks.append((cur_title, "\n".join(cur))); cur = []
            cur_title = line.lstrip("# ").strip()
        else:
            cur.append(line)
    if cur:
        blocks.append((cur_title, "\n".join(cur)))

    chunks = []
    for title, body in blocks:
        # 这里用字符数近似 token 数，实际请用分词器
        for i in range(0, max(len(body), 1), max_tokens - overlap):
            piece = body[i:i + max_tokens]
            chunks.append({"title": title, "text": f"[{title}]\n{piece}"})
    return chunks

9.48.4 嵌入与索引

嵌入模型的选择标准：在你的领域数据上做检索评测，不要看榜单。通用模型（如 bge-m3、e5）在通用语料好，但在法律、医疗上常常不如领域微调的小模型。

索引的三类结构：

结构原理特点
扁平（Flat）暴力算距离精确，百万级以内可接受
IVF先聚类再在簇内搜快，需要调 nprobe
HNSW多层可导航小世界图快且召回高，内存占用大
PQ/OPQ向量分段量化省内存，有精度损失

HNSW 是当前默认选择：M（每层连接数）与 ef_search 控制"召回 vs 延迟"的权衡。

9.58.5 混合检索：为什么必须有 BM25

纯向量检索对专有名词、编号、代码、缩写很弱——这些词的语义信息少，但精确匹配需求强。所以标准做法是双路：

\text{score}=\alpha\cdot\text{norm}(\text{BM25})+(1-\alpha)\cdot\text{norm}(\text{cosine})

或者各召回 20 条后用 RRF（倒数排名融合）合并。工程上更常用 RRF，因为它不需要分数归一化：

\text{RRF}(d)=\sum_{r\in\text{rankers}}\frac{1}{k+\text{rank}_r(d)}

9.68.6 重排：性价比最高的一步

召回 50 条，重排取 5 条。交叉编码器（query 与 doc 一起编码）比双塔精度高得多，代价是每个候选一次前向。50 个候选 × 200 token ≈ 10K token 的前向，在 GPU 上是几十毫秒级，完全可接受。

实测经验：加一层重排通常能把"答对率"提升 5–15 个点，是所有环节里性价比最高的。

9.78.7 组装：三个细节

  1. 顺序：把最相关的放在开头和结尾（模型对中间位置的注意力弱）；
  2. 引用：给每个块编号，要求模型在回答里标注来源，便于核查与追责；
  3. 冲突处理：检索到的内容互相矛盾时，提示模型"指出冲突"而不是随便选一个。

9.88.8 评估：两个正交的指标

指标测什么怎么测
检索质量（Recall@k、MRR）有没有找到正确片段人工标注 100 条 query 的正确块
生成质量（忠实度、相关性）回答是否基于检索内容人工或 LLM 判定

必须分开测。如果检索没找到，生成再好也是错的；如果检索对了但答错，问题在提示或模型。混在一起测，你永远不知道改哪里。

工程视角

RAG 上线后的头号问题是"答不出但看起来很自信"。三道防线：

1. 检索为空或最高分低于阈值 → 直接回答"没有找到相关资料"； 2. 强制引用：回答里每个结论都要有块编号，没有引用的句子视为不可信； 3. 抽样人工复核，把错误样本回流成新的评测集。

10.39.3 规划：三种粒度

粒度做法适用
无规划边想边做（ReAct）步骤少、路径不确定

经验：任务步数少于 5 步，ReAct 足够；超过 10 步，一定要有显式计划与进度记录，否则模型会迷路。

10.49.4 记忆：三层

层存什么实现
工作记忆当前任务的消息与中间结果上下文窗口（会被截断）
会话记忆跨轮次的关键事实摘要 + 结构化槽位
长期记忆用户偏好、历史结论外部存储 + 检索

最容易被忽略的是"摘要压缩"：长任务里上下文必然超限，需要定期把已完成步骤压成一段摘要。压缩策略要保留"结论与未完成项"，丢弃"过程细节"。

10.59.5 多智能体：什么时候值得拆

拆分的收益来自上下文隔离：不同角色只需要看自己相关的信息，上下文更短、更聚焦。拆分的代价是通信开销与一致性维护。

值得拆的信号：

  • 子任务需要完全不同的工具集；
  • 子任务可并行；
  • 需要独立评审（一个生成、一个挑错）。

不值得拆的信号：

  • 任务步骤少；
  • 强依赖共享上下文（拆开反而要反复传递）；
  • 团队没有能力维护多套提示与评测。

10.69.6 评测：智能体不能只看最终答案

维度指标采集方式
任务成功率端到端通过率固定任务集，人工或规则判定
步数效率平均步数 / 最优步数日志统计
工具正确率参数合法、调用必要日志 + 规则校验
成本token 与调用次数计量
安全越权、注入触发率红队测试集

最有效的评测方法是"轨迹回放"：把失败案例的完整消息序列拿出来，逐步骤看模型在哪一步判断错。这比看最终答案有用得多。

常见坑
  • 没有步数上限，遇到死循环时账单爆炸；
  • 工具没有幂等设计，重试导致重复下单/重复发邮件；
  • 把工具返回的原始 HTML/JSON 全塞进上下文，一次就撑爆窗口；
  • 让模型自己决定"要不要执行危险操作"，正确做法是让系统决定——模型只提议，权限在系统侧。

10　提示工程：有效约束与无效仪式

提示工程里真正有效的部分很少，但每一条都能被验证；剩下的都是玄学。

应用　·　约 1635 字　·　4 分钟

这一章刻意区分两类做法：能通过对比实验证明有效的，和主要靠心理安慰的。做过 A/B 的团队都知道，很多流行技巧换一个任务就不工作。

11.110.1 六条稳定有效的手段

手段为什么有效示例要点
明确任务与输出格式减少歧义，缩小搜索空间"输出 JSON，字段 a/b/c"
给示例（few-shot）用具体例子定义"好答案"的样子2–5 个覆盖不同情形
分解步骤把多步推理拆成可检查的小步"先列出已知，再计算"
提供材料让模型基于给定文本而非记忆引用块 + 编号
设定拒答条件给"不知道"一条合法出口"材料中无依据时回答：未找到"
约束长度与粒度避免冗长和跑题"不超过 5 句，每句一个结论"

这六条的共同点是：都在减少模型需要自己猜的东西。提示工程的本质是"接口设计"，不是"咒语"。

11.210.2 思维链：什么时候有用，什么时候没用

"让我们一步步思考"这类提示在多步算术、逻辑推理上确实有效，原因是它把隐式计算变成了显式 token，模型有更多计算预算。

但它有明确的适用边界：

  • 有效：需要多步推理、有中间量可以写出；
  • 无效甚至有害：简单任务（浪费 token）、需要直觉的任务（强行拆解反而错）、以及要求诚实报告推理过程的场景——模型写出的"推理"常常是事后编的，与实际决策路径不一致。

所以：要结果可靠性，用 CoT；要可解释性，不要指望 CoT 的文本是真因。

11.310.3 结构化输出：最工程化的部分

要求 JSON 有两种实现层次：

层次做法可靠性
提示约束在提示里要求 JSON 并给示例中，偶有格式错
JSON mode引擎层保证语法合法高
语法约束解码用 grammar/regex 约束 token 采样最高，字段与枚举都可强制

语法约束解码的原理：在每一步把不符合当前语法状态的 token 概率置零，再做采样。这只保证语法，不保证语义——模型可以生成完全合法但内容错误的 JSON。

python
# 伪代码：按语法状态过滤 logits
def constrained_logits(logits, parser_state):
    allowed = parser_state.allowed_tokens()   # 由 grammar 推导
    mask = torch.full_like(logits, -float("inf"))
    mask[allowed] = 0
    return logits + mask

11.410.4 上下文工程：比措辞更重要

同样一段材料，放在不同位置、不同长度，效果差异巨大。四条实证结论：

  1. 首尾优于中间（lost in the middle）。关键信息放开头或结尾；
  2. 无关内容会显著降低准确率，不是"多读点总没坏处"。宁少勿滥；
  3. 结构标记有效：用清晰的分隔符与编号，比自然语言段落好；
  4. 指令放在末尾比放在开头更容易被遵循（尤其在长上下文里）。

11.510.5 那些被高估的技巧

  • "请深呼吸""这对我的职业很重要"：个别模型上偶有微小提升，但不稳定，跨模型不通用；
  • 长篇人格设定：对风格有影响，对能力几乎无影响，还消耗上下文；
  • 堆叠大量"务必""必须""绝对"：过度强调会让模型在边界处过度谨慎或忽略其他要求；
  • 要求模型"证明自己正确"：会诱发编造论据。

判断标准很简单：同一批测试样本上做对比，差异是否稳定。没有对比数据的"技巧"不值得写进生产提示。

11.610.6 提示也需要版本管理

生产提示应该像代码一样管理：

  • 存版本（v1/v2），记录改动与对应指标；
  • 有回归测试集，改完跑一遍；
  • 关键提示的改动要走评审；
  • 记录"为什么这么写"（很多提示的约束是为了修某个具体 bug，不写清楚就会被后人删掉）。
工程视角

把提示当成配置 + 契约：输入输出的格式约定写在提示与后处理两侧，两边都要校验。只在一侧约束，另一侧迟早漂移。

12.111.1 私有评测集：最重要的一件事

做法：

  4. 固定版本：评测集一旦定版就不改，新增另开 v2，否则历史对比失效。

12.311.3 LLM-as-judge：能用，但要设计

用法可靠性说明

整体打分（1–10）低分数不稳定，不可比

必须做的三件事：

  1. 交换顺序消除位置偏置；
  2. 固定评分标准（写在 judge 提示里，逐条）；
  3. 与人工对齐验证：抽 50 条人工标一遍，算一致性（Cohen's kappa）。一致性低于 0.6 就不要用 judge 做主判据。

13.512.5 一个最小服务骨架

// 三件事：动态批、队列、超时
struct Req { std::string prompt; std::promise<std::string> done; };

void worker() {
    while (running) {
        std::vector<Req> batch;
        queue.wait_pop_batch(batch, /*max=*/8, /*wait_ms=*/5);  // 攒 5ms
        if (batch.empty()) continue;
        auto outs = engine.generate(batch_prompts(batch), /*max_new=*/256);
        for (size_t i = 0; i < batch.size(); ++i)
            batch[i].done.set_value(outs[i]);                    // 逐个兑现
    }
}

要点：攒批窗口要短（2–10ms），长了延迟明显；超时要独立于批处理，不能因为一个慢请求拖累全批；背压要早，队列满了直接 429，别无限堆积。

13.612.6 性能定位顺序

  1. 看 GPU 利用率：低 → 数据/调度瓶颈；高且吞吐低 → 带宽瓶颈；
  2. 拆 TTFT 与 TPOT：TTFT 高是 prefill 问题（长 prompt、chunk 太小）；TPOT 高是 decode 问题（权重大、量化不够）；
  3. 看显存：是否因 KV 溢出触发重算或换出；
  4. 最后才是换引擎。
工程视角

C++ 侧最大的两个收益点，往往不是"换更快的内核"，而是零拷贝（避免 host↔device 反复搬运）与批处理（把带宽瓶颈摊薄）。这两件事在 Python 层做不了，正好是你的战场。

13　成本与容量规划

成本 = 显存 ÷ 并发 × 时间。三个变量里，只有"单位时间产出"能被优化。

成本　·　约 1034 字　·　3 分钟

上线前必须能回答三个问题：能撑多少并发、单次请求多少钱、扩到十倍要加什么。这一章给可算的公式。

14.113.1 三笔成本

成本构成量级感受
训练GPU 小时 + 数据工程7B 全量训练数十万到百万美元级
推理GPU 小时 + 显存占用通常占长期成本的 80% 以上
运维人力 + 存储 + 监控常被低估，尤其是数据标注

推理成本是长期的、持续的、随用户增长线性上升的。所以推理优化（量化、批处理、缓存）的回报远高于训练优化。

14.213.2 容量公式

\text{并发上限}=\frac{\text{显存}-\text{权重}}{\text{单序列 KV}},\qquad \text{单序列 KV}=2LSH_{kv}d_{head}b

举例：24GB 卡跑 7B INT4（权重 3.5GB）+ 8 层系统占用，剩约 19GB；单序列 KV（4K 上下文）约 0.5GB → 约 36 路并发。如果上下文升到 16K，直接掉到 9 路。

\text{吞吐}=\frac{\text{并发}}{\text{每 token 时间}}\times\text{并发}\ \Rightarrow\ \text{tok/s}\approx\frac{B}{\text{TPOT}}

注意 TPOT 会随批增大而变长，所以吞吐不是线性增长，存在饱和点。

14.313.3 单位经济：一次问答多少钱

假设：

  • A10 实例 1.0 美元/小时；
  • 输入 1000 token、输出 300 token；
  • 实测吞吐 30 req/s（批处理下）。
\text{单次成本}=\frac{1.0}{3600\times30}\approx0.0000093\ \text{美元}

看起来可以忽略。但如果吞吐掉到 0.5 req/s（没有批处理、上下文很长），就变成 0.00056 美元/次，一天十万次是 56 美元——同一个模型，差 60 倍。

结论：成本不由模型大小决定，由"每 GPU 每小时能服务多少请求"决定。

from pypdf import PdfReader

def load_pages(pdf_path):
    pages = []
    for i, page in enumerate(PdfReader(pdf_path).pages):
        t = (page.extract_text() or "").strip()
        if len(t) > 20:                       # 过滤空白页/封面
            pages.append({"page": i + 1, "text": t})
    return pages

def chunk(pages, max_chars=400, overlap=80):
    out = []
    for p in pages:
        t = p["text"]
        for i in range(0, len(t), max_chars - overlap):
            piece = t[i:i + max_chars]
            if len(piece) < 30:
                continue
            out.append({"text": f"第{p['page']}页：{piece}",
                        "page": p["page"], "src": "doc.pdf"})
    return out

两个细节：前缀里带页码（让模型能引用），以及过滤过短的块（避免噪声）。

15.414.4 第 3 步：混合检索 + 重排

python
from rank_bm25 import BM25Okapi

def tokenize_zh(s):                       # 中文用字级简单切
    return list(s)

bm25 = BM25Okapi([tokenize_zh(c["text"]) for c in chunks])

def retrieve(query, k_recall=20, k_final=5):
    qv = enc.encode([query], normalize_embeddings=True)[0]
    scores = vecs @ qv                                  # 向量召回
    vec_rank = np.argsort(-scores)[:k_recall]

    bs = bm25.get_scores(tokenize_zh(query))            # 关键词召回
    kw_rank = np.argsort(-bs)[:k_recall]

    # RRF 融合（k=60 是常用常数）
    fused = {}
    for r, idx in enumerate(vec_rank):
        fused[idx] = fused.get(idx, 0) + 1 / (60 + r)
    for r, idx in enumerate(kw_rank):
        fused[idx] = fused.get(idx, 0) + 1 / (60 + r)
    top = sorted(fused.items(), key=lambda x: -x[1])[:k_recall]

    # 简易重排：用向量分数 + 命中词数做二次打分
    # 生产环境应换成 cross-encoder
    rescored = [(i, fused[i] * 0.6 + float(scores[i]) * 0.4) for i, _ in top]
    rescored.sort(key=lambda x: -x[1])
    return [chunks[i] for i, _ in rescored[:k_final]]

注意 RRF 不需要分数归一化，这是它比加权求和更好用的原因——两路分数尺度完全不同。

16.315.3 六条判断力

这些是比任何具体技术都长寿的东西：

  1. 先算账再优化。显存、算力、带宽三个数算不清，所有优化都是猜；
  2. 瓶颈通常在数据与链路，不在模型。RAG 的问题 90% 在检索；
  3. 能量化的改动才叫优化。没有评测集的改动只是"感觉变好了"；
  4. 优先用简单方法。能用 BM25 + 规则解决的，不要上向量库 + 重排；
  5. 对齐与安全是设计约束，不是上线前的补丁；
  6. 警惕"能力叙事"。任何"模型能自动完成 X"的说法，都要求一个失败率的数字。

16.515.5 最后一句话

AI 工程里最稀缺的能力，不是会用最新的模型，而是能把一个模糊需求拆成可测量的链路，并在每一环上做出有依据的取舍。这个能力和写 C++ 时做架构决策是同一种能力。

模型会换、框架会换、榜单会换。算账的能力、定位瓶颈的能力、以及"不轻信效果宣称"的习惯，不会过时。
